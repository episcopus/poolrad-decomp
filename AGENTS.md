# AGENTS.md: operating manual for AI agents

You are working on a **behaviour-matching decompilation of SSI's Pool of Radiance (DOS)** into readable C. This file is the canonical instruction set for every harness (Claude Code, Cursor, OpenCode, others). Read it fully at the start of every session.

## Read first

1. `docs/spec/SPEC.md`: goals, approach, verification ladder, phases. It wins over anything else except a direct human instruction.
2. `work/status.md`: where the project stands (generated by `make status`).
3. The playbook for your task in `docs/process/playbooks/` (index below).
4. `docs/design/WHITEPAPER.md`: what is already known about the game. Do not rediscover it; extend it.

## Facts you must not get wrong

- The original program is **Turbo Pascal 6.0 (June 1991 release)**, 16-bit real mode, with **35 overlay units** in `GAME.OVR` (`FBOV`) and **15 known resident units**: 13 in the init chain plus the Borland Dos (`res13`, `0A32`) and Overlay (`res14`, `0AA2`) units, which have no init. It is not C. Byte-matching C is impossible; we prove behaviour instead (SPEC section 4).
- Not TP 7.0 and not the October 1990 TP 6.0: our runtime units byte-match the June 1991 compiler only (`make tp-compare`, whitepaper 2.2). TP 6.0 has no `const` parameters and no `$Q`. POOL was compiled `$F+ $S- $R- $G-`, with `$I+` only in res05.
- The Turbo Pascal compiler is a proprietary reference tool: it lives in `build/toolchain/` (ignored by git) and is never committed, pushed or copied into `src/`.
- Analyse `poolrad/start-unpack.exe` (the unpacked image), not `START.EXE` (EXEPACK packed).
- Our build differs from the 1988 build other projects analysed (38 overlays, `TPOV`). Their addresses never apply to us; their findings are leads to re-prove.

## Ground rules

1. **Evidence or it did not happen.** Every name, type and claim cites an address, a tool output or a test. Prior art and your own recall are leads, tagged [H] until proven on our bytes.
2. **Tools write verdicts, you do not.** Never edit a verification level by hand. Never weaken a test, add a mask, or loosen a comparison without a written reason in the commit and a human's approval.
3. **Stay in your lane.** Lock the unit you work on (`make lock UNIT=...`). Edit only that unit's files plus `re/` entries for its routines. Shared headers and the platform API change only through the orchestrator.
4. **Never touch** `poolrad/` (pinned originals), `build/` contents in commits, or code from sources whose licence forbids reuse (see `docs/reference/prior-art.md`: coab, wicanr2, GPL projects are read-only references).
5. **Small commits.** One routine or a few related routines per commit. Message format: `<unit>: <what> (<routine ids>) [Lx]`.
6. **Stop and ask the human** before changing: the spec or an ADR, the memory model, `src/platform/platform.h`, the session set or `re/state.toml`, anything under `poolrad/`.
7. **Bounded effort.** After 5 failed fix attempts on one routine, stop, write a `blocked` note in `re/symbols.toml` (`notes`) with what you tried, and move on.
8. **Keep the design doc alive.** Each finished unit updates `docs/design/WHITEPAPER.md` and `docs/design/CHANGELOG.md` (playbook 60).
9. **Write plainly.** No em dashes or en dashes in any file or message; use commas, colons, semicolons or parentheses.

## Code conventions (summary; SPEC section 7 is authoritative)

- C99 subset, width types only (`u8 s16 u32` ...), no floats, no bitfields, no VLAs, no libc beyond `memcpy memset memmove strlen`.
- Globals live in the generated DGROUP mirror `G`; heap records via `farptr` + `FP(Type, p)`.
- One C function per original routine, provenance comment with address, unit, entry index and level.
- Faithful first, readable second; quirks are kept and documented, never silently fixed.
