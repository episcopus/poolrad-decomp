# 01: The CPU (Motorola 6809 / Hitachi 6309) for the Pool of Radiance CoCo 3 port

## Key takeaways for the Pool of Radiance port

1. The CoCo 3 CPU is a 68B09E clocked from the GIME: 28.636363 MHz / 32 = 0.894886 MHz at power-up, 28.636363 MHz / 16 = 1.789773 MHz after any write to $FFD9 (POKE 65497,0). Run the whole game at 1.79 MHz; that gives about 29,860 CPU cycles per 59.94 Hz NTSC field and about 113.75 cycles per scanline.
2. Cycle reality at 1.79 MHz: a byte fill can reach about 1.9 to 2.2 cycles per byte with unrolled PSHU (about 820 to 940 KB/s), a byte copy about 3.4 to 4.6 cycles per byte with PULU/PSHS (about 390 to 520 KB/s), and a naive C style `*d++ = *s++` loop is 15 to 20 cycles per byte (about 90 to 120 KB/s). A 32,000-byte 320x200x16 screen is 34 to 39 ms to clear and 60 to 80 ms to copy even with the best 6809 code.
3. On the integer, pointer and branch work that dominates Turbo Pascal game logic, a 6809 at 1.79 MHz is roughly level with the PC's 8088 at 4.77 MHz; it is much faster at 8x8 multiply (MUL is 11 cycles) and branches, and 1.5x to 6x slower at 16x16 multiply, division and 32-bit arithmetic, which have no hardware support on the 6809.
4. CMOC output is measurably weaker than gcc6809 (about 1.28x the code size and about 2x the cycles on a published benchmark set), so CMOC code at 1.79 MHz should be treated as roughly equal to TP 6.0 code on a 4.77 MHz 8088 for logic, and clearly too slow for pixel loops. Every per-pixel or per-byte loop (picture decode, 4bpp blits, tile drawing, text glyph rendering, frame-delta XOR) belongs in hand-written assembly.
5. Interrupt cost: IRQ takes 19 cycles to enter and RTI 15 to leave (entire state, 12 bytes); FIRQ takes 10 to enter and 6 to leave (PC and CC only). Use the GIME timer on FIRQ for the 236.7 Hz sound tick; at about 50 cycles per tick that is under 1% of the CPU.
6. The 6309 (native mode: about 15% faster on unmodified code, TFM block move at 3 cycles per byte, MULD 28 cycles, DIVD 25, DIVQ 34) is an enthusiast upgrade, not a baseline. Ship a pure 6809 build, and keep 6309 as an optional assembly-level fast path. CMOC generates 6809 code only; LWASM accepts 6309 instructions by default, so assemble baseline code with `--6809` (or `PRAGMA 6809`) to catch accidents.
7. Code size: about 200 KB of x86 TP code will likely become 200 to 300 KB of 6809 code through CMOC (an estimate; no direct x86 vs 6809 measurement exists). It must be overlaid through the GIME MMU, exactly as the PC version overlays GAME.OVR.

## 1. Programming model

| Register | Width | Notes |
|---|---|---|
| A, B | 8 | Accumulators. |
| D | 16 | A:B concatenated, A is the high byte (src: MC6809E datasheet, https://colorcomputerarchive.com/repo/Documents/Datasheets/MC6809E%20HMOS%208%20Bit%20Microprocessor%20(Motorola)%20(OCR).pdf). |
| X, Y | 16 | Index registers. Instructions that load/store/compare Y need a $10 prefix byte: one extra byte and one extra cycle versus X (LDX imm 3 cycles/3 bytes, LDY imm 4/4). |
| U | 16 | User stack pointer, fully under program control; also an index register. PSHU/PULU make it a second stack. CMOC uses U as its frame pointer. |
| S | 16 | Hardware stack used by JSR/BSR/RTS and interrupts. Also an index register; LDS/STS/CMPS need a prefix. |
| PC | 16 | PC-relative indexed addressing (`n,PCR`) gives position-independent code. |
| DP | 8 | Direct page: supplies the high address byte for direct-mode instructions. Cleared at reset. |
| CC | 8 | E F H I N Z V C. E = entire state was stacked (tells RTI how much to pull); F = FIRQ mask; I = IRQ mask; H = half carry (src: same datasheet). |

There is no 16-bit register-to-register add or compare on the 6809 (no `ADD D,X`); the only register-register arithmetic is ABX (X += B unsigned), LEA with A/B/D offsets, MUL (D = A*B), SEX and DAA. This is the biggest structural difference from x86 for compiled code: anything x86 keeps in a second register, the 6809 spills to memory (usually the stack, a frame slot or the direct page).

## 2. Addressing modes and their cost

Base cycle counts (Motorola reference card, src: https://colorcomputerarchive.com/repo/Documents/Datasheets/MC6809-MC6809E%20Reference%20Card%20(Motorola).pdf):

| Mode | Example | Bytes | Cycles (LDA) | Cycles (LDD) |
|---|---|---|---|---|
| Immediate | `LDA #$12` | 2 (LDD 3) | 2 | 3 |
| Direct (DP:nn) | `LDA <$40` | 2 | 4 | 5 |
| Extended | `LDA $1234` | 3 | 5 | 6 |
| Indexed | `LDA ,X` | 2+ | 4+ | 5+ |

Indexed postbyte table, extra cycles / extra bytes added to the indexed base (src: MC6809E datasheet Table 2, and the reference card; both agree):

| Form | Postbyte | Non-indirect +cyc/+bytes | Indirect `[...]` +cyc/+bytes |
|---|---|---|---|
| `,R` | 1RR00100 | +0 / +0 | +3 / +0 |
| `n,R` 5-bit (-16 to +15) | 0RRnnnnn | +1 / +0 | not allowed |
| `n,R` 8-bit | 1RR01000 | +1 / +1 | +4 / +1 |
| `n,R` 16-bit | 1RR01001 | +4 / +2 | +7 / +2 |
| `A,R` | 1RR00110 | +1 / +0 | +4 / +0 |
| `B,R` | 1RR00101 | +1 / +0 | +4 / +0 |
| `D,R` | 1RR01011 | +4 / +0 | +7 / +0 |
| `,R+` | 1RR00000 | +2 / +0 | not allowed |
| `,R++` | 1RR00001 | +3 / +0 | +6 / +0 |
| `,-R` | 1RR00010 | +2 / +0 | not allowed |
| `,--R` | 1RR00011 | +3 / +0 | +6 / +0 |
| `n,PCR` 8-bit | 1xx01100 | +1 / +1 | +4 / +1 |
| `n,PCR` 16-bit | 1xx01101 | +5 / +2 | +8 / +2 |
| `[nnnn]` extended indirect | 10011111 | n/a | +5 / +2 |

RR selects X=00, Y=01, U=10, S=11. Because the register is in the postbyte, indexed accesses through Y or S cost the same as through X or U; only the Y/S-specific opcodes (LDY, STY, CMPY, LDS...) pay the prefix.

Practical consequences:
- `,X` (0) and small offsets (+1, no extra byte) are the sweet spot. Glen Hewlett's measurements show that unrolled stores with 5-bit offsets plus one ABX beat auto-increment: `STU ,X++` costs 5+3 = 8 per 2 bytes, `STU n,X` costs 5+1 = 6 (src: https://nowhereman999.wordpress.com/2017/09/15/optimizing-6809-assembly-code-part-2-speedup-storing-data-unrolling-loops/).
- 16-bit offsets (+4) bite on the CoCo 3 because a 320-pixel 4bpp row is 160 bytes, beyond the 8-bit offset range. Step rows with `LDB #160 / ABX` (2+3 = 5 cycles, B must be free) or `LEAX 160,X` (4+4 = 8).
- `D,R` and indirect modes are expensive (+4, +7); avoid them in inner loops. `A,R`/`B,R` (+1) are cheap but signed; ABX is unsigned and 2 cycles faster than `LEAX B,X` (src: Hewlett part 2, above).

Notes and source disagreements:
- PSH/PUL: "The PSH and PUL instructions require 5 cycles plus 1 cycle for each byte pushed or pulled" (reference card). PC, U/S, Y, X count 2 bytes each; A, B, DP, CC 1 each. So `PSHU D,X,Y` = 5+6 = 11, `PULU D,X,Y,DP` = 5+7 = 12, `PULS D,X,Y,PC` (pull and return) = 5+8 = 13. MAME's PULS/PULU microcode drops one internal cycle in native mode, consistent with 4+n.
- The HD63B09EP guide lists native RTS as "5 (1)"; that "1" is a scan or typesetting error. Kakugawa's 6309 memo gives RTS 5 (4) (src: https://en.wikichip.org/wiki/hitachi/6309/a_memo_on_the_secret_features_of_6309) and MAME removes exactly one dummy cycle from RTS in native mode. Use 4.
- The same guide is inconsistent about native RTI (6/15 (17) in one table, 6/17 and 15/17 in another). MAME and the stacking arithmetic (two more bytes for W) give 6 for a FIRQ frame and 17 for a full native frame.
- The 6309 numbers above apply only in native mode (MD bit 0 = 1). In emulation mode the 6309 uses 6809 cycle counts.
- Pulling with U is cheaper than auto-increment loads: `PULU D` is 7 cycles vs `LDD ,U++` 8; `PULU Y` is 7 and 2 bytes vs `LDY ,U++` 9 and 3 bytes. PULU does not set flags; LD does (src: https://nowhereman999.wordpress.com/2017/09/16/optimizing-6809-assembly-code-part-4-odds-and-sods-more-tricks/).
- `LEAX ,U` (4) is the cheap TFR U,X (6); `LEAX -1,X / BNE` (5+3) is the cheapest 16-bit loop counter because LEAX/LEAY set Z (LEAU/LEAS do not) (src: Hewlett parts 1 and 4).

## 4. CoCo 3 clock and speed

### What the clock really is

- The CoCo 3 has a 2 MHz-rated 68B09E (the CoCo 1/2 used a 1 MHz 6809E) (src: https://www.cocopedia.com/wiki/Color_Computer_3). Datasheet ratings: MC6809E 1.0 MHz, MC68A09E 1.5 MHz, MC68B09E 2.0 MHz (src: MC6809E datasheet, above).
- The CPU E clock is derived from the 28.636363 MHz video crystal (8 x the 3.579545 MHz NTSC colour burst). MAME models it as `XTAL(28'636'363) / 32` for the base rate, and the SAM-compatible speed bits in the GIME halve the divider: CPU clock = master / (divider x 2) when R1 or R0 is set, / (divider x 4) when clear (src: https://raw.githubusercontent.com/mamedev/mame/master/src/mame/trs/coco3.cpp line 388, https://raw.githubusercontent.com/mamedev/mame/master/src/devices/machine/6883sam.cpp `update_cpu_clock`).
  - Slow: 28,636,363 / 32 = 894,886 Hz (the "0.89 MHz").
  - Fast: 28,636,363 / 16 = 1,789,773 Hz (the "1.79 MHz", often written 1.78).
  - PAL CoCo 3: 28.475 MHz / 32 = 889,844 Hz slow, 1,779,688 Hz fast (src: coco3.cpp line 486).
- Switching: write any value to $FFD9 (R1 set) for fast, $FFD8 for slow (POKE 65497,0 and POKE 65496,0) (src: 6883sam.cpp comment block; https://cocopedia.com/wiki/index.php/Color%20Computer%20FAQ). On the CoCo 3 the screen keeps working at the fast rate; on a CoCo 1/2 R1 corrupted the display (src: 6883sam.cpp comment). The machine powers up slow (src: cocopedia CoCo 3 page).
- Useful derived budgets at 1,789,773 Hz: 558.7 ns per cycle; 29,860 cycles per 59.94 Hz field; about 113.75 cycles per 15,734 Hz scanline. [derived]

### Is 1.79 MHz safe for disk I/O and the ROM?

Sources are thin and not fully consistent:
- "300 Pokes Peeks 'n Execs for the CoCo III" lists POKE &HFFD9,0 as "Doubles the speed of all operations" with the remark "Affects disk/printer I/O" (src: https://colorcomputerarchive.com/repo/Documents/Books/300%20Pokes%20Peeks%20'n%20Execs%20for%20the%20CoCo%20III%20(Microcom%20Software).pdf). It does not say whether disk I/O fails or merely runs faster.
- The CoCopedia FAQ says the crystal also times "the printer, cassette, and serial ports, plus disk drive operation" (in the context of replacing the crystal), and that the third-party ADOS "runs the CoCo at double-speed, even during disk and printer I/O", implying that stock Disk BASIC was not designed for it (src: https://cocopedia.com/wiki/index.php/Color%20Computer%20FAQ).
- What is mechanically timing-sensitive: the bit-banger serial/printer port and cassette routines are pure software timing loops and will break at double speed. The WD1773 floppy byte transfer is synchronised with HALT/NMI so the CPU rate does not matter for it; the risk is the ROM's software delays (motor spin-up, head settle), which become half as long. [unverified: inferred from the controller design; not confirmed from a source in this pass]
- NitrOS-9 on a CoCo 3 runs permanently at 1.79 MHz with its own floppy drivers. [unverified]

Recommendation: the game does not need the BASIC ROM except possibly DSKCON for sector reads. Test DSKCON at 1.79 MHz early in XRoar, MAME and on real hardware. If any doubt remains, bracket each DSKCON call with `STA $FFD8` ... `STA $FFD9` (a few cycles each; use STA not CLR on these registers, CLR does an extra read and is a cycle slower, src: Hewlett part 1, https://nowhereman999.wordpress.com/2017/09/14/optimizing-6809-assembly-code-part-1-quick-and-easy-changes-to-speedup-your-code/). A custom disk driver should use its own delay loops calibrated for 1.79 MHz.

### Effective memory throughput

Measured and computed rates at 1.789773 MHz (cycles per byte from source listings; KB/s = 1,789,773 / cycles per byte / 1024):

| Method | Cycles per byte | KB/s at 1.79 MHz | Source |
|---|---|---|---|
| `STU ,X++ / CMPX #end / BNE` (2 bytes/iteration) | 7.5 | 233 | Hewlett part 2: 61,440 cycles for 8,192 bytes |
| Same with DECB/DECA counters | 6.5 | 269 | Hewlett part 2: 53,328 cycles |
| 16 x `STU n,X` + ABX, offsets to 30 | 3.2 | 546 | Hewlett part 2: 26,368 cycles |
| 5 x `PSHU D,X,Y` + `PSHU D` + CMPU/BHI (fill) | 2.19 | 798 | Hewlett part 2: 70 cycles per 32 bytes, 17,920 for 8,192 |
| 26 x `PSHU D,X,Y` + `PSHU D,X` per 160-byte row (fill) | 1.89 | 925 | derived from the PSH rule |
| `PSHU D,X,Y,DP` unrolled (fill, DP holds the pattern byte) | 1.71 | 1,020 | derived; DP is unusable during the fill |
| `PULU D,X,Y,DP / PSHS D,X,Y,DP / CMPU / BLO` (copy) | 4.57 | 382 | Hewlett part 3: 32 cycles per 7 bytes |
| Same unrolled 4x, data pre-arranged in "stack order" | 3.6 | 485 | derived |
| Forward copy in true order with PULU/PSHS + `LEAU -14,U` | about 4.4 | about 395 | derived (see cookbook 2) |

So a 320x200x16 frame (32,000 bytes) costs about 60,000 to 70,000 cycles (34 to 39 ms) to fill and 110,000 to 146,000 cycles (61 to 82 ms) to copy. The 6309's TFM copies faster than any 6809 copy but fills slower than PSHU stack blasting (3 vs about 2 cycles per byte).

## 5. Hitachi 6309

### Modes and registers

- MD register (write with `LDMD #n`, test with BITMD): bit 0 = 0 emulation mode, 1 native mode; bit 1 (FM) = 0 normal FIRQ, 1 FIRQ behaves like IRQ (stacks everything); bit 6 set by illegal-instruction trap; bit 7 set by divide-by-zero trap; all zero after reset (src: HD63B09EP Technical Reference Guide; Kakugawa memo https://en.wikichip.org/wiki/hitachi/6309/a_memo_on_the_secret_features_of_6309).
- New registers: E, F (8-bit accumulators), W = E:F (16-bit), Q = D:W (32-bit), V (16-bit, survives reset, reachable only through inter-register ops), and the zero register 0 (reads as zero, writes discarded; usable as a TFM source/destination address register per the guide) (src: HD63B09EP guide; "The 6309 Book", https://colorcomputerarchive.com/repo/Documents/Books/The%206309%20Book%20(Burke%20&%20Burke).pdf).
- All new instructions and registers work in both modes; native mode additionally shortens many instruction timings ("15% typical speed increase") and saves/restores W during interrupts (src: The 6309 Book).

### New instructions that matter for the port

| Instruction | What | Cycles (emulation / native) | Source |
|---|---|---|---|
| TFM r0+,r1+ / r0-,r1- / r0+,r1 / r0,r1+ | Block move of W bytes; the fixed-address forms copy to or from a port, or fill (`TFM X,Y+` with X pointing at the fill byte) | 6 + 3n | HD63B09EP guide; MAME hd6309.lst |
| MULD | D x operand (signed 16x16) to Q (32-bit) | imm 28; direct 30 (29); ext 31 (30); +2 if an operand is negative | guide; hoglet67 wiki |
| DIVD | D / 8-bit operand: quotient in B, remainder in A | imm 25; direct 27 (26); ext 28 (27); +1 per negative operand | guide; hoglet67 wiki |
| DIVQ | Q / 16-bit operand: quotient in W, remainder in D | imm 34 (the opcode table of the guide says 36; the mnemonic table and Kakugawa say 34); direct 36 (35); ext 37 (36) | guide; Kakugawa |
| AIM / OIM / EIM / TIM | AND/OR/EOR/TEST an immediate into memory without touching a register | direct 6; indexed 6+ to 7+; extended 7 (TIM ext 5 per one table) | guide; Kakugawa |
| ADDR / SUBR / ANDR / ORR / EORR / CMPR / ADCR / SBCR | Register-to-register arithmetic, e.g. `ADDR X,D` | 4, 3 bytes | guide; Kakugawa |
| LDQ / STQ | 32-bit load/store | LDQ imm 5; direct 8 (7); ext 9 (8) | guide |
| LDW / STW, ADDW, etc. | 16-bit W ops | LDW imm 5 (4); direct 6 (5); ext 7 (6) | guide |
| PSHSW / PULSW / PSHUW / PULUW | Push/pull W | 6, 2 bytes | guide |
| Bit ops BAND, BOR, BEOR, LDBT, STBT | Single-bit moves between a register bit and a direct-page bit | [not checked] | Kakugawa |

TFM detail: it is the only interruptible instruction; on an interrupt it backs PC up and restarts, and the last byte read is read again (src: HD63B09EP guide; https://www.sbprojects.net/sbasm/6309/notes.php; MAME TFM comment). Reading an I/O port with TFM is therefore unsafe; writing to one is safe (src: https://github.com/hoglet67/6809Decoder/wiki/Undocumented-6309-Behaviours). Do not use `TFM r-,r-` to build a stack (src: sbprojects notes).

Speed-ups in native mode for the hot instructions (6809 vs native): ABX 3 vs 1, TFR 6 vs 4, EXG 8 vs 5, RTS 5 vs 4, JSR ext 8 vs 7, BSR 7 vs 6, LBSR 9 vs 7, PSH/PUL 5+n vs 4+n, LDA/LDD direct one cycle less, CMPX/ADDD direct 6 vs 4, MUL 11 vs 10 (src: HD63B09EP guide).

### Interrupts in native mode

- An entire-state frame grows from 12 to 14 bytes (W is pushed after D: CC, A, B, E, F, DP, X, Y, U, PC from low to high) (src: HD63B09EP guide; MAME `entire_state_registers()` returns 0x3FF in native mode vs 0xFF, https://raw.githubusercontent.com/mamedev/mame/master/src/devices/cpu/m6809/hd6309.h). IRQ entry becomes 21 cycles, SWI 21, RTI of a full frame 17. [IRQ 21 derived from MAME microcode: 3 internal + 14 stacked bytes + 4 vector/internal]
- FIRQ still stacks only PC and CC (10 cycles) unless FM (MD bit 1) is set, in which case it stacks the full 14-byte frame like IRQ (src: MAME hd6309.h `firq_saves_entire_state()`; guide).

### Compatibility pitfalls

- Any handler or OS code that reads or patches values at fixed offsets in an interrupt frame (`LDD 1,S` style access to stacked A/B, `STD 10,S` to change the return PC) breaks in native mode, because E and F shift X, Y, U, PC up by two bytes. This is why "many programs can be executed in 6309 native mode by patching only the IRQ code, if it accesses the stack" (src: https://www.sbprojects.net/sbasm/6309/notes.php).
- Under RS-DOS, native mode made disk, printer and cassette use "affected and unreliable" because ROM timing loops got shorter; RS-DOS users saw about 10 to 15% gains, OS-9 users with patches (PowerBoost, NitrOS-9 6309 builds) 30 to 50% (src: https://cocopedia.com/wiki/index.php/Color%20Computer%20FAQ).
- 6809 undocumented opcodes and undocumented index postbytes (0x92, 0xB2, 0xBF, 0xD2, 0xDF, 0xF2, 0xFF) trap on the 6309 through the $FFF0 vector, which is shared with divide-by-zero (src: hoglet67 wiki). Never use undocumented 6809 opcodes in the port.
- Native-mode errata: wrong flags pushed when SYNC follows a single-cycle instruction; NMI during SWI or CWAI can mis-fetch the handler's first byte (src: hoglet67 wiki). Avoid SYNC immediately after one-cycle instructions in native mode.
- Do not change MD mode while an interrupt frame is on the stack: RTI pulls 12 or 14 bytes depending on the current mode, not the mode at push time. [unverified: inferred from MAME's `entire_state_registers()` being evaluated at RTI time]
- Flag differences: H is unaffected (not undefined) after ASL/ASR/CMP/NEG/SBC/SUB; DAA differs from the 6809 for some inputs with C=1 (src: hoglet67 wiki). TP's BCD-free code does not care.

### How common is the 6309?

No census exists. It was "one of the biggest pieces of news to come out in the early 1990s" and installation requires desoldering the 6809 (src: CoCopedia FAQ). NitrOS-9 ships separate 6309 builds (src: CoCopedia FAQ), MAME has a 6309 CoCo 3 machine (`HD6309E(config.replace(), ...)` in coco3.cpp line 501), and XRoar has `-machine-cpu 6309` (src: https://www.6809.org.uk/xroar/doc/xroar.shtml). [unverified: a large share of active CoCo 3 owners have a 6309, but it is clearly not universal]

### Toolchain support

- LWASM: `--6309` / `-3` enables 6309 instructions and "is the default mode"; `--6809` / `-9` rejects 6309-only instructions, equivalent to `PRAGMA 6809` (src: https://www.lwtools.ca/manual/c62.html). Put `PRAGMA 6809` at the top of every baseline assembly file, or pass `--6809`.
- CMOC: its manual and home page describe a 6809 target only; neither mentions the 6309 (src: http://perso.b2b2c.ca/~sarrazip/dev/cmoc-manual.html, http://perso.b2b2c.ca/~sarrazip/dev/cmoc.html). There is no 6309 code generator, so a 6309 speed path must come from hand-written assembly and from running CMOC's 6809 code in native mode (gaining about 15% for free, as long as our own interrupt handlers handle the 14-byte frame). Check `cmoc --help` in the 0.1.100 container for any newer flag. [unverified for 0.1.100; the fetched manual covers 0.1.44]

## 6. Interrupts

| Source | Vector | Stacks | Entry cycles (6809) | Return | Masks set |
|---|---|---|---|---|---|
| NMI | $FFFC | Entire state, 12 bytes | 19 | RTI 15 | I and F |
| IRQ | $FFF8 | Entire state, 12 bytes | 19 | RTI 15 | I |
| FIRQ | $FFF6 | PC and CC only, 3 bytes, E=0 | 10 | RTI 6 | I and F |
| SWI | $FFFA | Entire state | 19 | RTI 15 | I and F |
| SWI2 / SWI3 | $FFF4 / $FFF2 | Entire state | 20 | RTI 15 | none |

Sources: FIRQ "stacks only the contents of the condition code register and the program counter" and IRQ "stacks the entire machine state" so "provides a slower response" (MC6809E datasheet, above); SWI 19 and SWI2/3 20 and RTI 6/15 (reference card); IRQ 19 and FIRQ 10 entry derived from MAME microcode (two dummy reads + one internal cycle, the stacked bytes, then one internal cycle + two vector reads + one internal cycle: 3 + 12 + 4 = 19 and 3 + 3 + 4 = 10) (src: base6x09.lst and m6809.lst). The level-sensitive FIRQ and IRQ lines need to stay low for at least three cycles to be guaranteed to be taken (src: MC6809E datasheet).

Latency: worst case is the remaining time of the instruction in progress plus entry. The longest common 6809 instructions are about 20 cycles (CWAI 20, SWI 19, `PULS` of everything 17, `JSR [n16,X]` 14); on a 6309 DIVQ/MULD run 28 to 37 cycles and TFM is interruptible. So FIRQ latency is at most about 30 cycles (17 us at 1.79 MHz), IRQ at most about 39.

On the CoCo 3 the hardware vectors in ROM point to RAM jump slots; the FIRQ slot is a JMP at $FEF4 with its target at $FEF5 (Hewlett patches `$FEF5` to end FIRQ audio playback, src: https://nowhereman999.wordpress.com/2017/09/16/optimizing-6809-assembly-code-part-3-stack-blasting-and-self-modifying-code/). The IRQ slot is $FEF7. [unverified: other slots] The GIME routes its timer, VBORD/HBORD and keyboard sources to IRQ via $FF92 and to FIRQ via $FF93, and reading those registers acknowledges pending interrupts (src: https://raw.githubusercontent.com/mamedev/mame/master/src/mame/trs/gime.cpp lines 729 to 736 and 893 to 950). The GIME timer counts 12-bit values from $FF94/$FF95 at either the 63.5 us line rate or a 279 ns rate (master/8; Tandy's docs say 70 ns but MAME and Gault's FAQ say 279 ns) (src: gime.cpp comments at lines 433 to 436 and `reset_timer`). Details belong in the GIME research file.

Why games use FIRQ: entry plus exit is 16 cycles instead of 34, and the handler saves only what it touches. A minimal timer tick for Pool's 236.7 Hz sound timer:

```
; FIRQ handler, assembled into RAM so self-modification is legal
firq:   sta   firq_a+1     ; 5  save A into the LDA below (self-modifying; saves a byte and a cycle vs PSHS A)
        lda   $FF93        ; 5  acknowledge GIME FIRQ
        dec   <snd_ticks   ; 6  count down the current sound step (DP variable)
        bne   firq_a       ; 3
        ...                ;    step the effect: write next DAC / PSG value, reload <snd_ticks
firq_a: lda   #$00         ; 2  restore A (operand patched above)
        rti                ; 6
```

Fast path about 10 + 5 + 5 + 6 + 3 + 2 + 6 = 37 cycles; at 236.7 Hz that is about 8,800 cycles per second, 0.5% of the CPU. By contrast, synthesising PC-speaker square waves in software through the 6-bit DAC at, say, 8 kHz with about 40 cycles per sample would cost 320,000 cycles per second (18%). [derived] Keep sound at the tick rate and use hardware tone generation where the target sound hardware allows it (see the sound research file).

Pattern from Hewlett's CoCo 3 FIRQ audio player: store A into the restore instruction's operand, step the sample pointer with `INC <LoadAudio+2` inside the code itself, and stop playback by pointing the FIRQ slot at an RTI (src: Hewlett part 3).

## 7. Optimisation idioms used by CoCo game coders

1. Direct page for hot variables. `LDD <var` is 5 cycles and 2 bytes vs 6 and 3 extended (src: Hewlett part 2). Put the game's hottest globals (current party member, cursor, loop counters, pointers into the current overlay's data) in one 256-byte page and set DP once. CMOC "does not use or modify" DP (src: CMOC manual), so DP belongs to the hand-written asm. Remember `SETDP` so the assembler picks direct mode (src: https://docs.retrogamecoders.com/assembly/6809/).
2. Self-modifying code. Immediate operands are the fastest storage: `LDA #n` is 2 cycles vs 4 direct and 5 extended. Patch loop bounds into `CMPU #imm` (5), saved registers into `LDA #imm`/`LDS #imm` restores (saves 3 cycles and 2 bytes for S, src: Hewlett part 3). The 6809 has no cache, so SMC is always coherent; it only fails for code in ROM.
3. Unrolled loops with small offsets. Unroll so loop overhead (DECB/BNE 5 cycles, CMPX/BNE 7 to 8) is spread over 16 to 32 bytes, and use 5-bit offsets plus one ABX or LEA per pass rather than auto-increment (3.2 vs 7.5 cycles per byte in Hewlett's measurements, part 2).
4. Stack blasting. Point U (or S, with interrupts masked) at the end of the destination and `PSHU D,X,Y` to write 6 bytes in 11 cycles. With S as the data pointer, an interrupt pushes its frame below S, so either mask interrupts (`ORCC #$50`) or make sure the area below S is scratch. U is safe with interrupts enabled.
5. Copy with two stacks. `PULU regs` from the source and `PSHS regs` to the destination; 7 bytes per 24 cycles with D,X,Y,DP (src: Hewlett part 3). Blocks come out in reverse order (see cookbook 2), which is free if the stored data (save-under buffers for menus, pre-baked pictures) is stored in "stack order".
6. Lookup tables instead of computation: row start addresses (200 x 2 bytes), nibble expansion tables for the 1-bit font (16 entries x 2 bytes gives four 4bpp pixels per nibble), colour remap tables (EGA index to GIME palette slot), pixel masks.
7. 16-bit arithmetic in D. Use LDD/ADDD/STD instead of two 8-bit adds: `LDD $1F00` (6) beats `LDA $1F00 / LDB $1F01` (10) (src: Hewlett part 1). Prefer CMPX over CMPD/CMPY/CMPU (one byte and one cycle less) and LDX/LDU over LDY/LDS.
8. MUL is cheap for 8x8: 11 cycles. `LDA #160 / LDB <y / MUL` gives the 4bpp row offset for y up to 255 in 17 cycles, about the same as a table (`LDX #tab / LDB <y / ABX / ABX / LDX ,X` = 3+4+3+3+5 = 18). What to avoid is 16x16 multiply and all division: see cookbook 6 for an 84-cycle 16x16 multiply; replace multiplies by constants with shifts and adds, and replace loop multiplies by strength reduction (running pointers). gcc6809 does this automatically; CMOC inlines MUL for small constants (src: https://vectrex.substack.com/p/cmoc-vs-vbcc-vs-gcc6809).
9. U as a second stack and pointer: `PULU D` is faster than `LDD ,U++`; streaming data through PULU is the fastest way to read sequential input (RLE source, sprite data).
10. Tail calls and combined returns: `BRA sub` instead of `BSR sub / RTS` saves 9 cycles; `PULS D,X,Y,PC` instead of `PULS D,X,Y / RTS` saves 3 (src: Hewlett part 1).
11. Put the unlikely path on the long branch: LBcc is 5 not taken and 6 taken; or `Bcc around / JMP far` for a rarely taken far target (src: Hewlett part 1, credited to Sockmaster).
12. Compiled sprites: generate code per sprite that stores immediates (`LDD #pix / STD n,X`), skipping transparent bytes and masking only mixed bytes. A GUI generator exists for the CoCo (src: https://github.com/pfiscarelli/CoCo_Sprite_Compiler). Fastest possible, but costs 2 to 3 bytes of code per sprite byte.

## 8. Code density: 6809 vs 8086

No published measurement compares the same C (or Pascal) compiled for x86 and for the 6809. Weaver's code density study hand-codes a benchmark in assembly on 30+ architectures but does not include the 6809 (src: https://web.eece.maine.edu/~vweaver/papers/iccd09/, https://web.eece.maine.edu/~vweaver/papers/iccd09/ll_document.pdf). The comparison below is reasoned from instruction sizes. [estimate]

The one compiler measurement that exists is 6809-only (src: https://vectrex.substack.com/p/cmoc-vs-vbcc-vs-gcc6809): over 11 small game kernels, total code size was CMOC 0.1.67 1,333 bytes, CMOC 0.1.98 1,214, vbcc 1,188, gcc6809 948; whole-program Pong was CMOC 1,092, vbcc 874, gcc6809 789. Normalised to gcc6809 = 1.00, CMOC 0.1.98 is 1.28x in size and 1.99x in cycles. CMOC emits a U frame-pointer prologue (`PSHS U / LEAU ,S / LEAS -n,S`) on every function; `-fomit-frame-pointer` (CMOC 0.1.82 and later) shrinks code further (memops 54 to 40 bytes, isort 99 to 94).

Typical TP 6.0 x86 sequences vs plausible CMOC 6809 sequences:

| Operation | x86 (TP style) | Bytes | 6809 (CMOC style) | Bytes |
|---|---|---|---|---|
| Load local word | `MOV AX,[BP-4]` | 3 | `LDD -4,U` (5-bit offset) | 2 |
| Store local word | `MOV [BP-4],AX` | 3 | `STD -4,U` | 2 |
| Load global word | `MOV AX,[nnnn]` | 3 | `LDD nnnn` (or 2 via DP) | 3 |
| Add constant | `ADD AX,5` | 3 | `ADDD #5` | 3 |
| Compare and branch | `CMP AX,5 / JL x` | 5 | `CMPD #5 / BLT x` | 6 |
| Two-register add | `ADD AX,BX` | 2 | `ADDD -6,U` (operand spilled) | 2 + spill store 2 |
| Byte array element via far pointer | `LES DI,[BP+6] / MOV BX,[BP-2] / MOV AL,ES:[BX+DI]` | 10 | `LDX 6,U / LDD -2,U / LDB D,X` | 6 |
| Far call, 2 word args | `PUSH [BP-2] / PUSH [BP-4] / CALL FAR p` | 11 | `LDD -4,U / PSHS D / LDD -2,U / PSHS D / JSR p / LEAS 4,S` | 13 |
| Function prologue (stack check on) | `PUSH BP / MOV BP,SP / MOV AX,n / CALL FAR StackCheck / SUB SP,n` | about 13 | `PSHS U / LEAU ,S / LEAS -n,S` | 6 |

Reasoning: the two ISAs have similar per-instruction density for memory-to-accumulator code (2 to 3 bytes), which is what both TP 6.0 and CMOC emit (neither keeps values in registers across statements). The 6809 loses where x86 has a second free register (spills), on 16-bit compares (CMPD is 4 bytes), and on 32-bit and multiply/divide helpers; it wins on the elimination of segment registers and far pointers (TP code is full of LES/ES: overrides and 5-byte far calls between units), on short branches, and on TP's per-procedure stack-check calls. Expect CMOC output for the game logic in the range 0.9x to 1.5x the x86 byte count, so 180 to 300 KB for the 197,641 bytes of x86 code. [estimate] This only holds if the C is rewritten to native 16-bit pointers; compiled as-is with the flat-arena far-pointer emulation, it would be much larger.

## 9. Throughput: 6809 at 1.79 MHz vs 8088 at 4.77 MHz

8088 facts used: every 8088 bus access is 4 cycles (0.838 us at 4.77 MHz) and moves one byte; the prefetch queue fills at one byte per 4 cycles, which "is the ultimate limit on overall instruction execution time" (src: Abrash, Zen of Assembly Language, https://www.phatcode.net/res/224/files/html/ch04/04-02.html and .../04-03.html). Intel timings: MOV reg,mem 8+EA (12+EA for words on the 8088), MOV mem,reg 9+EA (13+EA), EA 5 to 12; MUL r8 70 to 77, MUL r16 118 to 133; MOVS 18 (26 for words on the 8088) (src: https://panthema.net/2006/helppc21/HelpPC-2.10-HTML/asm-Instruction_Timing.html, asm-mov.html, asm-mul.html, asm-movs.html). REP MOVSB 9+17n, REP STOSB 9+10n, DIV r16 144 to 162, Jcc 16 taken / 4 not, near CALL 19, RET 16 are from the Intel 8086 manual as I recall them. [unverified]

The 6809 at 1.79 MHz makes one bus access per cycle (1.79 M accesses per second) vs 1.19 M for the 8088, which is why it holds its own despite the lower clock.

| Operation | 8088 @ 4.77 MHz | 6809 @ 1.79 MHz | 6309 native @ 1.79 MHz |
|---|---|---|---|
| Load local word | `MOV AX,[BP+d8]` 12+9 = 21 cyc, 4.4 us | `LDD n,U` 6 cyc, 3.4 us | 3.4 us |
| Add word from memory | `ADD AX,[BP+d]` about 22, 4.6 us | `ADDD n,U` 7, 3.9 us | 6, 3.4 us |
| Register add | `ADD AX,BX` 3 (prefetch bound about 8), 1.7 us | no reg-reg; via stack `ADDD ,S++` 9, 5.0 us | `ADDR X,D` 4, 2.2 us |
| Conditional branch taken | 16, 3.4 us | 3, 1.7 us | 1.7 us |
| Near call + return | 19+16 (+8 for word pushes on 8088) about 43, 9 us [unverified] | `JSR`+`RTS` 13, 7.3 us | 11, 6.1 us |
| 8x8 multiply | `MUL r8` 70 to 77, 15 us | `MUL` 11, 6.1 us | 10, 5.6 us |
| 16x16 multiply (low 16 bits) | `MUL r16` 118 to 133, 26 us | about 84 (cookbook 6), 47 us | `MULD` 28, 16 us |
| 16/16 divide | `DIV r16` 144 to 162, 32 us [unverified] | software, about 250 to 400, 140 to 220 us [estimate] | `DIVQ` 34 to 36, 20 us (or `DIVD` 25 for 16/8) |
| 32-bit add (longint in memory) | about 4 instr, about 80 cyc, 17 us [estimate] | 34 cyc (cookbook 6), 19 us | `LDQ/ADDW/ADCD/STQ` faster [not computed] |
| Copy 32,000 bytes | `REP MOVSW` about 25 per word, 400k cyc, 84 ms [derived] | 3.6 to 4.6 c/b, 61 to 82 ms | TFM 3 c/b, 54 ms |
| Fill 32,000 bytes | `REP STOSW` about 14 per word, 224k cyc, 47 ms [derived] | 1.9 to 2.2 c/b, 34 to 39 ms | same (TFM fill is slower) |

But the PC did not move 32,000 bytes per full-screen EGA update: EGA 320x200x16 is planar, so with write mode 0/2 and set/reset or latch copies (write mode 1) one CPU byte access touches 8 pixels in all four planes (8,000 addresses per screen), at the cost of ISA wait states. [unverified: EGA wait-state figure not checked] The CoCo 3's packed 4bpp mode needs a byte per 2 pixels, so pixel-heavy operations need about 4x the CPU bus traffic of the EGA equivalents.

### Which parts of Pool of Radiance will be CPU bound on the CoCo 3

Ordered by likely cost (estimates at 1.79 MHz with assembly inner loops):

1. DAX decompression plus picture conversion. A 32,000-byte title picture through RLE decode at about 7 to 11 cycles per output byte is 230,000 to 350,000 cycles (0.13 to 0.2 s), plus any nibble or palette remap pass. Acceptable at load time; CMOC-compiled decode would be several times slower.
2. 3D view rendering from 8x8 tiles: about 230 cycles per opaque tile (cookbook 3); for a view of roughly 11 x 11 tiles [unverified size] that is about 28,000 cycles (16 ms). Fine per move, provided tiles are pre-converted to 4bpp packed format at load time.
3. Animated pictures with XOR frame deltas: `LDA ,U+ / EORA n,X / STA n,X` is about 15 cycles per byte; a 40x88 portrait-sized region (1,760 bytes) is 26,000 cycles per frame (15 ms). Pre-convert deltas to "skip/run" lists if frames are large.
4. Text: 40x25 cells of the 1-bit 8x8 font expanded to 4bpp (32 bytes per glyph) through a nibble table is about 300 to 400 cycles per glyph; a full 1,000-cell redraw is 0.2 s, so redraw only changed cells.
5. Tactical combat map with 24x24 icons: about 1,500 cycles per compiled icon, 4,000 to 6,700 with a generic masked loop (cookbook 4); redrawing a whole map screen of a few dozen icons is tens of milliseconds. Fine.
6. Game logic in CMOC: combat AI, pathfinding, the ECL bytecode VM, character generation and the rules engine. TP code with 16-bit Integer and some Longint math. Expect it to run at about the PC's speed, slower where it multiplies, divides or uses Longint. The ECL VM dispatch loop is the one place in logic code worth hand-tuning (opcode jump table via `JMP [B,X]`-style dispatch or `LDX tab / ASLB / JMP [B,X]`).
7. Disk I/O (DAX loads, overlay swaps, saved games) will dominate perceived latency more than the CPU does; see the disk research file.

Not CPU bound: menus (poll keyboard), sound (timer tick), delays.

## 10. Inner loop cookbook

All cycle counts are 6809 at the stated rate; multiply by 0.5587 us for time at 1.79 MHz. Screen stride is 160 bytes (320 pixels x 4bpp, high nibble = left pixel, which matches the DAX packing and the GIME 16-colour modes). DP-relative variables are shown as `<name`.

### Cookbook 1: memory fill (screen or buffer clear) with PSHU

```
; fill160 - fill R rows of 160 bytes, from the bottom row up
; In:  U = address one past the last byte to fill (end of region)
;      D = 16-bit pattern (e.g. $1111 for colour 1 in both nibbles)
;      <rows = number of 160-byte rows (1..255)
; Interrupts may stay enabled: U is not the system stack.
fill160:
        tfr   d,x            ; 6   X = pattern
        leay  ,x             ; 4   Y = pattern
frow:   pshu  d,x,y          ; 11  x26 = 156 bytes, 286 cycles
        pshu  d,x,y
        ; ... (26 copies in total, generated with a macro / REPT)
        pshu  d,x            ; 9   4 more bytes = 160
        dec   <rows          ; 6
        bne   frow           ; 3
        rts
; Per row: 286 + 9 + 9 = 304 cycles for 160 bytes = 1.90 cycles/byte.
; 200 rows (32,000 bytes): 60,800 cycles = 34.0 ms at 1.79 MHz.
; Code size: 26*2 + 2 + 2 + 2 = 58 bytes for the unrolled row.
```

Variant: with DP free (no direct-page code running), `PSHU D,X,Y,DP` writes 7 bytes in 12 cycles (1.71 c/b) if the pattern bytes are all equal (DP holds one byte), but the row counter must then live in a register or an extended address. With interrupts masked and S saved by self-modification, `PSHU D,X,Y,S` writes 8 bytes in 13 cycles (1.63 c/b); rarely worth the risk.

### Cookbook 2: forward block copy with two stacks

```
; copy7 - copy N*7 bytes, preserving order, src and dst not overlapping
; In:  U = src_end - 7   (start with the LAST 7-byte block of the source)
;      dst_end patched into the LDS below, src start patched into CMPU
; Uses S as the destination pointer, so IRQ/FIRQ must be masked.
copy7:  pshs  cc             ;     save interrupt mask
        sts   restore+2      ; 7   self-modifying save of S
        orcc  #$50           ; 3   mask IRQ and FIRQ
        lds   #$0000         ; 4   patched: dst_end (one past last dest byte)
cloop:  pulu  d,x,y,dp       ; 12  read 7 bytes ascending (A,B,DP,X,Y)
        pshs  d,x,y,dp       ; 12  write the same 7 bytes below S, same order
        leau  -14,u          ; 5   back up to the previous source block (5-bit offset)
        cmpu  #$0000         ; 5   patched: src_start (loop while U >= src_start)
        bhs   cloop          ; 3
restore lds   #$0000         ; 4   patched with the saved S
        puls  cc,pc          ;     restore mask and return
; Per 7 bytes: 12+12+5+5+3 = 37 cycles = 5.3 c/b. Unrolled 4x (move CMPU/BHS
; outside the group): 4*29+8 = 124 per 28 bytes = 4.4 c/b, about 395 KB/s.
; If the data is stored pre-reversed in 7-byte blocks ("stack order", e.g. a
; save-under buffer written by the same routine run the other way), drop the
; LEAU: 24 cycles per 7 bytes plus loop, 3.4 to 3.6 c/b.
; DP is clobbered: reload it (or push it) if direct-page code runs next.
```

Why the LEAU: PULU walks up, PSHS walks down, so each 7-byte block lands in the right order internally but successive blocks are reversed; walking the source backwards fixes it.

6309 equivalent: `LDW #n / TFM X+,Y+` at 6+3n cycles; interruptible, so no masking needed.

### Cookbook 3: opaque 8x8 tile blit (3D view walls, 4bpp packed)

D carries pixel data, so the 160-byte stride cannot live in B for ABX. Use 16-bit offsets instead and leave X fixed:

```
; tile8 - copy one 8x8 tile (4 bytes x 8 rows, stored contiguously, 32 bytes)
; In:  U = tile data, X = screen address of the tile's top-left byte
; Out: U advanced by 32; X unchanged
tile8:
        pulu  d,y            ; 9   row 0 bytes 0..3 (A,B = bytes 0,1; Y = bytes 2,3)
        std   ,x             ; 5
        sty   2,x            ; 7   (STY indexed 6 + 5-bit offset 1)
        pulu  d,y            ; 9   row 1
        std   160,x          ; 9   (5 + 16-bit offset 4)
        sty   162,x          ; 10  (6 + 4)
        pulu  d,y            ; 9   row 2
        std   320,x          ; 9
        sty   322,x          ; 10
        ; rows 3..7 at offsets 480, 640, 800, 960, 1120: 28 cycles each
        rts                  ; 5 (or inline the tile and drop JSR/RTS)
; Cycles: row 0 = 21, rows 1..7 = 28 each = 196; total 217 + JSR/RTS 13 = 230.
; 121 tiles (an 11 x 11 tile view): about 27,800 cycles = 15.6 ms.
```

Alternative: point X at row 4 (`LEAX 640,X` once) so rows 3..5 can use 8-bit offsets (-160 does not fit, so no gain); 16-bit offsets are simply the cost of a 160-byte stride. A faster option for whole wall faces is to keep each wall graphic pre-rendered at screen stride in its own buffer and copy it with cookbook 2.

### Cookbook 4: 24x24 combat icon with transparency (4bpp)

Data format prepared at load time: for each of the 12 bytes in each of 24 rows, a mask byte (nibble $F where the pixel is transparent, $0 where opaque) followed by a pixel byte (0 in transparent nibbles). Generic loop:

```
; icon24 - masked blit of a 24x24 4bpp icon, byte aligned (x even)
; In:  U = mask/pixel pairs (576 bytes), X = screen top-left byte
icon24: lda   #24
        sta   <rows          ; 4
irow:   lda   ,x             ; 4    byte 0
        anda  ,u+            ; 6    keep background where transparent
        ora   ,u+            ; 6    merge icon pixels
        sta   ,x             ; 4
        lda   1,x            ; 5    byte 1 (5-bit offsets for bytes 1..11)
        anda  ,u+            ; 6
        ora   ,u+            ; 6
        sta   1,x            ; 5
        ; ... bytes 2..11 identical with offsets 2..11 (22 cycles each)
        leax  160,x          ; 8    next row (16-bit offset)
        dec   <rows          ; 6
        bne   irow           ; 3
        rts
; Per row: 20 + 11*22 + 17 = 279 cycles; 24 rows = 6,696 cycles = 3.7 ms.
; Unrolled row code: about 4*12*2 = 96 bytes plus loop.
```

Faster, by classifying bytes at load time:
- fully transparent byte: emit nothing (0 cycles);
- fully opaque pair of bytes: `LDD #pp / STD n,X` = 3 + 5 or 6 = 8 to 9 cycles for 2 bytes;
- mixed byte: `LDA n,X / ANDA #m / ORA #p / STA n,X` = 5+2+2+5 = 14 cycles.
For a typical icon (about 60% opaque, 25% transparent, 15% mixed of 288 bytes) a compiled sprite is about 692 + 602 + 192 (row steps) = about 1,500 cycles (0.84 ms), about 4.5x faster than the generic loop, at about 600 to 900 bytes of code per icon. Use compiled icons for the handful on screen in a combat (player party and current monster types), generated into a RAM cache when combat starts; use the generic loop for everything else. Odd-x placement (nibble shifted) needs a second pre-shifted copy; the combat map is on a 24-pixel grid so all icons are byte aligned.

On the 6309, the generic loop can use `PULU D` (6 native) for mask+pixels, `ANDA n,X`, `ORR B,A` (4) and `STA n,X`: about 20 cycles per byte native, barely better; compiled sprites remain the big win.

### Cookbook 5: DAX byte RLE decode

Format (from the decomp): code byte c < $80: copy the next c+1 bytes literally; c >= $80: repeat the next byte 256-c times.

```
; daxrle - decode one DAX block
; In:  U = packed source, X = destination
;      destination end address patched into the CMPX at 'chk' (self-modifying)
; Out: X = destination end, U = first byte after the packed data consumed
daxrle:
next:   ldb   ,u+            ; 6   code byte (LDB sets N; PULU B would not)
        bmi   run            ; 3
        incb                 ; 2   count = c+1 (1..128)
        lsrb                 ; 2   count/2, C = odd
        bcc   lpair          ; 3
        lda   ,u+            ; 6   odd byte first
        sta   ,x+            ; 6
        tstb                 ; 2
        beq   chk            ; 3
lpair:  pulu  y              ; 7   two literal bytes
        sty   ,x++           ; 9   (STY indexed 6 + ,R++ 3)
        decb                 ; 2
        bne   lpair          ; 3   21 cycles per 2 bytes = 10.5 c/b
        bra   chk            ; 3
run:    negb                 ; 2   B = 256-c ($80 -> 128, $FF -> 1)
        lda   ,u+            ; 6   byte to repeat
        sta   ,x+            ; 6   always at least 1
        decb                 ; 2
        beq   chk            ; 3
        sta   <tmp           ; 4   build a 16-bit pattern AA in Y
        sta   <tmp+1         ; 4
        ldy   <tmp           ; 6
        lsrb                 ; 2   remaining/2, C = odd
        bcc   rpair0         ; 3
        sta   ,x+            ; 6
        tstb                 ; 2
        beq   chk            ; 3
rpair0:
rpair:  sty   ,x++           ; 9
        decb                 ; 2
        bne   rpair          ; 3   14 cycles per 2 bytes = 7 c/b
chk:    cmpx  #$0000         ; 4   patched: destination end
        blo   next           ; 3
        rts
; Literal runs: about 10.5 cycles per output byte + about 25 per token.
; Repeat runs: about 7 cycles per output byte + about 45 per token.
; A 32,000-byte picture that is half literals and half runs, with 2,000
; tokens: about 168,000 + 112,000 + 70,000 = 350,000 cycles = 0.2 s.
; A naive byte loop (LDA ,U+ / STA ,X+ / DECB / BNE, 17 c/b) would be
; about 0.3 s; CMOC-compiled C typically 2x to 3x slower again. [estimate]
```

For long repeat runs into a buffer, stack blasting (set U' to dst+count, `PSHU D,X,Y` with the pattern) would reach 2 c/b, but needs extra setup per token; only worth it if profiling shows long runs dominate (large flat areas in title pictures).

If the target layout differs from the DAX layout (e.g. pictures narrower than the screen), decode into a linear buffer first and copy rows with cookbook 2, or add a per-row end check in place of the single end check.

### Cookbook 6: 16-bit and 32-bit idioms

```
; 16-bit add constant to a DP variable             cycles bytes
        ldd   <v                                  ; 5    2
        addd  #k                                  ; 4    3
        std   <v                                  ; 5    2   = 14 / 7

; 16-bit increment of a DP variable (usual case 9 cycles)
        inc   <v+1                                ; 6    2
        bne   1f                                  ; 3    2
        inc   <v                                  ; 6    2   (only on carry)
1:

; 16-bit compare and branch, unsigned (Word) vs signed (Integer)
        ldx   <v                                  ; 5
        cmpx  #limit                              ; 4   (CMPD would be 5 and 4 bytes)
        blo   below                               ; 3   unsigned: BLO/BHS/BHI/BLS
        ;  signed TP Integer compares need BLT/BGE/BGT/BLE instead

; Pointer + unsigned byte, pointer + signed byte, pointer + word
        abx                                       ; 3   X += B (unsigned)
        leax  b,x                                 ; 5   X += B (signed!)
        leax  d,x                                 ; 8   X += D

; Count-down loop on X without touching D (LEAX sets Z)
loop:   ...
        leax  -1,x                                ; 5
        bne   loop                                ; 3

; 32-bit add, a += b, both in DP, big-endian (TP Longint must be byte-swapped
; when loading PC data: x86 is little-endian, 6809 is big-endian)
        ldd   <a+2                                ; 5
        addd  <b+2                                ; 6
        std   <a+2                                ; 5
        ldd   <a                                  ; 5
        adcb  <b+1                                ; 4
        adca  <b                                  ; 4
        std   <a                                  ; 5   = 34 cycles

; Row address for a 160-byte stride, y in 0..199
        lda   #160                                ; 2
        ldb   <y                                  ; 4
        mul                                       ; 11  D = y*160 (max 31,840)
        addd  #SCREEN                             ; 4
        tfr   d,x                                 ; 6   = 27 (or LEAX D,Y with Y=SCREEN: 8)

; 16x16 -> low 16 bits multiply (a, b, t in DP)
mul16:  lda   <a+1                                ; 4   al
        ldb   <b+1                                ; 4   bl
        mul                                       ; 11  al*bl
        std   <t                                  ; 5
        lda   <a                                  ; 4   ah
        ldb   <b+1                                ; 4   bl
        mul                                       ; 11  low byte of ah*bl
        addb  <t                                  ; 4
        stb   <t                                  ; 4
        lda   <a+1                                ; 4   al
        ldb   <b                                  ; 4   bh
        mul                                       ; 11  low byte of al*bh
        addb  <t                                  ; 4   B = high byte of result
        tfr   b,a                                 ; 6
        ldb   <t+1                                ; 4   D = a*b mod 65536
        rts                                       ; 5   = 84 + 5 cycles
; 6309: LDD <a / MULD <b  -> Q = a*b (32-bit), 4 + 29 native.
```

Endianness is a porting trap independent of the CPU speed: every 16-bit and 32-bit value read from DAX archives, GEO maps, ECL scripts, character and item records and saved games is little-endian, and the 6809 is big-endian. Byte-swap at load time (or read with `LDB ,X / LDA 1,X`, 9 cycles vs LDD 5) and keep the on-disk format unchanged if PC save compatibility matters.

## Implications and recommendations for the port

1. Switch to 1.79 MHz at startup (`STA $FFD9`) and stay there; verify disk reads at 1.79 MHz early and keep a `$FFD8` bracket around DSKCON as a fallback.
2. Budget CPU in cycles per field: about 29,860 at 1.79 MHz. Anything over about 5 fields of work per keypress (150,000 cycles) will feel slow; that is roughly one full-screen copy plus a 3D view redraw.
3. Write these in hand-tuned LWASM assembly from the start, behind small C-callable entry points (args in registers or a DP parameter block, not CMOC's stack convention): DAX RLE decode, picture and palette conversion, 8x8 tile blit, masked and compiled icon blit, 1bpp glyph expansion, XOR frame-delta apply, rectangle fill and save-under copy, line drawing inner loop, memory copy/fill, the FIRQ sound tick. Everything else starts as CMOC C.
4. Reserve one direct page for asm hot variables and parameter passing; CMOC leaves DP alone. Do not let CMOC-compiled code depend on DP.
5. Pre-convert all graphics to the native 4bpp packed layout (and colour indices to GIME palette slots) at DAX load time, so the blitters never touch nibble remapping.
6. Use FIRQ from the GIME timer for the 236.7 Hz sound tick, IRQ (or polling) for everything else; keep handlers in RAM so they can use self-modifying save/restore.
7. Mask interrupts only around S-based stack blasts; prefer U-based routines so the sound FIRQ keeps running during fills and decodes.
8. Treat the 6309 as an optional speed path: build with `PRAGMA 6809` by default; a 6309 build can switch on native mode (all our interrupt handlers must then handle 14-byte IRQ frames and leave FM clear), use TFM in copies and MULD/DIVQ in the math helpers. Detect the CPU at boot (a 6309 test sequence, see Open questions) rather than requiring it.
9. Plan for 6809 code at 0.9x to 1.5x the x86 size, so 180 to 300 KB: MMU-banked overlays are mandatory, and the overlay boundaries should follow the existing 35 TP overlay units.
10. Evaluate `-fomit-frame-pointer` and the current CMOC peephole level on real game modules early, and measure cycles in MAME or XRoar; if CMOC's 2x speed gap vs gcc6809 matters for logic code, gcc6809 is the alternative for hot C modules (at the cost of a second toolchain).
11. Avoid 16-bit multiply and divide in hot logic paths (replace by shifts, tables, strength reduction); provide hand-written `mul16`, `div16`, `mul32` helpers and check what CMOC's runtime uses.
12. Byte-swap every multi-byte field from PC data files at load time; isolate it in the data layer.

## Open questions

- Does the RS-DOS (Disk BASIC 2.1) DSKCON routine work reliably at 1.79 MHz on real CoCo 3 hardware with real drives? Sources do not settle it; needs a test.
- Exact native-mode IRQ entry cycles and RTI on real 6309 silicon (21 and 17 here are derived from MAME and the stacking rule; the Hitachi guide's tables are inconsistent).
- Does CMOC 0.1.100 have any 6309 option, register calling convention or DP variable support? The manual fetched covers 0.1.44; run `cmoc --help` in the container.
- Does CMOC invoke lwasm with `--6809`? If not, inline asm could silently use 6309 opcodes; check the command line CMOC prints with `--verbose`.
- Whether LWASM's listing can print per-line cycle counts (an `OPT c`-style pragma) for asm review [unverified; not found in the fetched manual pages].
- How many CoCo 3 owners have a 6309 (no census found).
- Precise 8088 numbers for the comparison table (REP MOVS/STOS, DIV, CALL/RET) were not confirmed from a source in this pass.
- Exact dimensions of the Pool 3D view window and combat map, to replace the "11 x 11 tiles" assumption in the cost estimates (the decomp's video units know this).
- Darren Atkinson's "Motorola 6809 and Hitachi 6309 Programming Reference" (archive Books folder) could not be fetched in this pass; it is the best single reference to cross-check every number in section 3 and should be downloaded into the repo by hand.
- A safe 6309 detection sequence for boot (commonly done by executing a 6309-only instruction that behaves as a harmless documented or undocumented op on the 6809); needs a sourced, tested routine.
