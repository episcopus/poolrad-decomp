`make match UNIT=ovl09`: unit complete (14 matched, 1 nested, 0 differ). `make readability UNIT=ovl09`: clean.
`make stubs`: every stub header matches re/symbols.toml. No `inline`, `db` or `assembler` in the unit.

Main problem: the unit's central table is misnamed. DS:5582 (`RaceRow`) is the ITEMS type table, not a race
table: the loader fills it from record 2 of the ITEMS file, $810 bytes = 129 rows of 16 bytes (ovl11:05CD,
whitepaper 4.3, and the Loader paragraph that reads `OpenGameFile('ITEMS', ...)`). The unit itself indexes it
by item type everywhere (`RaceRow[Target^.ItemType]`, `RaceRow[Byte(Who^.SlotItems[0]^.ItemType)]`, POOLVARS
comment on SlotItems: "ovl19 indexes the slots by RaceRow[ItemType][0]"), and `UseBestItem` calls
`ScoreTarget(Who, PCharacter(Pick))` with an ITEM cast to a character. The `Race`, `HpMax` and `KnownSpells`
fields ScoreTarget reads are the item record's own bytes seen through the wrong record type: TCharacter.Race
(+$2E) is TItem.ItemType (+$2E), HpMax (+$32) is Plus, KnownSpells[4] (+$36) is Cursed, KnownSpells[$0B]/[$0C]
(+$3D/+$3E) are Affects[2]/Affects[3] (the same bytes UseMagicItem reads as the item's spell). So ScoreTarget
scores an item, not a foe, and the whitepaper 5.5.3 paragraphs on ScoreTarget and UseBestItem describe the
wrong thing ("known-spell bytes", "the candidate's race"). Row bytes then read as ITEMS fields (whitepaper 4.3:
slot, hands, dice, bonus, attacks, range, classFlags, flags): Row[0] is the slot, Row[1] the hands used (which
is what `ds100` counts: hands in use, 3 minus it tested against Row[1]), Row[12] the range, Row[13] the
class mask tested against the character's PadB0, Row[14] the flags.

## Findings

- [ ] must-fix RaceRow / TRaceRow (POOLVARS, used by ScoreTarget 128D, UseBestItem 13CA, AiTurn 0B3C, UseMagicItem 049F): the name says race table, the data is the ITEMS type table (ovl11:05CD loads the ITEMS file into DS:5582; the unit indexes it with ItemType in every routine). Rename it (`make rename`) to an item table name and TRaceRow to an item row type, with the row byte meanings from whitepaper 4.3 as named constants or a record (Row[0] slot, [1] hands, [12] range, [13] class mask, [14] flags), and fix the POOLVARS comments ("indexed by race") that repeat the error.
- [ ] must-fix ScoreTarget (128D): named and described as a rating of a foe (parameter Foe, "the foe's race, HpMax and known-spell bytes"); its only caller passes an item (`ScoreTarget(Who, PCharacter(Pick))`, 13CA), and the bytes it reads are item fields (+$2E ItemType, +$32 Plus, +$36 Cursed, +$3D/+$3E Affects[2]/[3]). Rename (an item scoring routine), take a PItem parameter (check that it still matches), replace `Foe^.Race`, `Foe^.HpMax`, `Foe^.KnownSpells[..]` by the item fields, and rewrite the comment in game terms. The $55 item type, the $84 and $53 values and `ShortInt(Row[11])` need names or `Purpose unknown` with the evidence. `Actor^.ds100` (hands in use) and `Actor^.ByteA0` are also read as the actor's state with no meaning given.
- [ ] must-fix UseBestItem (13CA): the comment and the whole routine are described through the wrong model ("pays the two per-kind slot items", "ScoreTarget on the item record", "best type-1 item by its Plus") and the name is too vague for what is item selection for the weapon and armour slots (SlotItems[0], [1], ovl19_e7 which ovl08 and the whitepaper call Ready Item). Once the table is known as ITEMS, rewrite the comment so a porter can follow it (what each of AttackPick/OtherPick/PlusPick is in game terms, what `Best`, `Score2`, `Best2`, `Row14`, `SlotFound`, `BothKinds`, `SlotUsable` hold), rename the weak locals (`Score2`, `Best2`, `Pick`, `Unused1/2` are fine as frame filler only), and name the bare numbers: Row indexes 0, 1, 12, 13, 14, the flag bits 1, 8, $10, $80, mask $14, the value $0A, the slot numbers 11 and 12 (+$F8, +$FC), and the thresholds 2 (hands). The unmarked `ovl09:1543` reference in the ScoreTarget comment must be checked.
- [ ] must-fix TCharacter fields ds100, dsA3, dsA5, dsA7, PadB0 (POOLVARS, used by UseBestItem and ScoreTarget): still dsXXX or Pad names although this unit gives them a role. `ds100` is the number of hands in use (compared with Row[1], the ITEMS hands byte), `PadB0` is the character's class bit tested against the item's class mask (Row[13]), `dsA3 * dsA5 + 2 * dsA7` is a combat score of the character's own attack. Name them with the evidence or give each a `Purpose unknown:` comment that says what is proven; today they have a two-line aside only.
- [ ] must-fix ovl09_fn_0203 (0203): "Purpose unknown" is wrong, the evidence is in ovl08. The routine tests `Combat^.Turned = 0` and `ClassLevels[0] > 0` and then calls ovl13_e9, which are exactly CombatMenu's condition for offering "Turn" (ovl08:0795/305) and PlayerTurn's `T Turn (ovl13_e9)` (ovl08:220). It is the AI taking the Turn (Turn Undead) action. Rename (for example `TryTurnUndead`), say so in the comment, and drop "Purpose unknown". Also QuickTurn's comment and whitepaper 5.5.3 call it "the level-0 turn", which says nothing; replace with the Turn action.
- [ ] must-fix CheckMorale (10D7), comment: it reverses the last branch. The code is `if E20Result <= ovl13_e2(Who) div 2 then (+$14 := 1, RemoveAffect $4A, $4B) else if Intelligence > 5 then (DropCombatant(Who, 4, 'Surrenders'), result := res12_fn_2637)`. The comment says survivors with the good roll "and Intelligence above 5 offer surrender" and "the rest get two RemoveAffect affects", and it never says that the RemoveAffect branch sets the panic byte +$14 to 1 (the character flees). Rewrite it to match the control flow (the failed morale check on the low roll panics the character; a higher roll with Intelligence above 5 surrenders; otherwise nothing).
- [ ] must-fix CheckMorale (10D7), comment and Globals line: the second morale test reads `ds49D6^[710]` (the second game variable block, $6B00..$6EFF, POOLVARS ds49D6) but the comment says "game word 710" and the whitepaper says `GameVars^[710]`. GameVars is the first block (`GameVars^[VarNoCasting]` in UseMagicItem is word 229 of it); two different blocks are called the same. Say ds49D6 in the comment, list it under Globals (it is missing; only ds6825, ds6E2F are listed), and use a constant for word 710 (ovl10 already names it `Var2Morale`, src/OVL10.PAS:85, "at most 100 (StartBattle); B84 morale source"; share it through POOLVARS). Also whitepaper 5.5.3 "a failed check makes a monster of side 1 flee" does not match the code (`or (Who^.Side = 0)` makes the party side always take the roll).
- [ ] must-fix CastMemorizedSpell (0545), Globals line and whitepaper 5.5.3 "Magic first": the comment lists `GameVars (word 710)` and the whitepaper says that both UseMagicItem and CastMemorizedSpell give up when `Combat+2` is zero and `VarNoCasting` is set. CastMemorizedSpell reads neither GameVars nor `Pad2`; it gates on `Combat^.CanCast <> 0` (+1) when collecting the spells, on `B84 > $7F` or the Magic toggle ds6E30, and on `ds6814Sides` of the side. Only UseMagicItem tests Pad2 (+2) and VarNoCasting. Fix both texts; the "Magic On/Off" gate (`(B84 > $7F) or ds6E30`) is not in the comment at all.
- [ ] must-fix AiTurn (0B3C), QUIRK text: "the +$CC deref runs before its nil test" is false. The `SlotItems[0]` test at 0C3E..0C48 (`or ax, [di+0xce]`, `je 0xc68`) precedes the deref at 0C4A. The real quirk is the unprotected one at 0C8E..0C91: `Target := Combat^.Target` is dereferenced (`Target^.Flag10D`, `Target^.Side`, 0C91, 0C9C) before the nil test at 0CAC, so a character with no remembered target reads through a nil pointer. Correct the comment and mark that quirk with its address.
- [ ] must-fix AiTurn (0B3C): meaningful numbers left bare: `$14` as the Initiative value is `InitiativeQuickAll` (already a constant of this unit, used by HandleCombatKey) in `Initiative < $14` and `= $14`; `I > $14` is the 20-turn limit; `$FF` and `1` are the Range sentinel and the ovl13_e21 arguments; hook numbers `$0E`. Name the turn limit and use the existing constant. (The comment also says "stumbles ($14 set: no step)", which means nothing; say that Initiative 0 or $14 ends the turn without acting.)
- [ ] must-fix QuickTurn (000F), MoveStep (07F2), AiTurn (0B3C), CanAffordStep (0675), CheckMorale (10D7): `PByteArray(Who^.Combat)^[$14]` and `[$15]` (and `[$10]` via `Pad10`) are used 14 times as the panic flag and the step pattern, both described in the comments by those names. Meaningful record offsets must be record fields: TCombatant is allocated with $16 bytes (whitepaper 5.5.1, PrepareCombatants zeroes $16) so +$14 and +$15 are inside the block, and the comment "lies past TCombatant" in CheckMorale only reflects that the type stops at +$13. Add the fields (additive, POOLVARS) `Panic` and `StepPattern` and `Pad10` as what CheckMorale shows it is (+$10 nonzero forces flight, "is forced to flee"), then use them. The byte at +$2 (`Pad2`, UseMagicItem) is likewise a named field in the whitepaper text ("combat byte +2") but still a Pad.
- [ ] should-fix UseMagicItem (03E4): local `Level` holds `Affects[2]`, a spell number (after `- $17` above MaxSpell), and is passed to SpellAccepted's `Spell` parameter; the name misstates it and the comment ("level from Affects[2]") and whitepaper ("the spell level") repeat it. In CastMemorizedSpell the same word `Level` is the Range (it is passed as SpellAccepted's `Range`). Call the first `SpellNumber`/`ItemSpell`, the second `Range`. Also the comment says "both ds6814Sides zero" but the code tests one entry, the actor's side (`ds6814Sides[res12_fn_23B7(Who)]`), and it does not say that Range starts at 7 and falls by one per round. As for the $17 offset and Affects[3] below $80: say what they are (an item spell stored as a scroll-style number above $38?) or mark them `Purpose unknown`.
- [ ] should-fix SpellAccepted (02EB): `SpellTable[Spell].PadB[$D]`, `[$E]`, `[$F]` are three record bytes the code depends on and the comment names (maximum range, "area" flag, ScanTargets line budget); put them in TSpellEntry as fields with the evidence already collected (packet learning "spell-row-tail-bytes", [I]). `Spell = 3` needs a named constant or a comment saying which spell it is and why ovl13_e13 decides it. `Tries` is the number of enemies found (res12_fn_2433 result), not tries; rename it. `DifferentSideInArea` is marked "Purpose unknown" although the code and the comment show it: it answers whether the area would reach a combatant of the other side from the one res12_fn_23B7 returns, which reads as an ally check; drop the sentence or say what is missing.
- [ ] should-fix MoveStep (07F2): the bare numbers in the party facing arithmetic `PartyFacing - (((PartyFacing + 2) mod 4) div 2)` and `+ 4` are not explained (the comment only says "derives a direction"); `Step < 6`, `Step = 6` (no affordable step) and the pattern count `mod 6 + 1` need a name for 5 columns and the "none found" value; `ClassMask = 5` is the magic-user (TCharacter comment says 5 is magic-user) and should be a constant. ## Verdict

Not passed: the item table is called RaceRow and ScoreTarget/UseBestItem are described as scoring foes by race and known spells, the Turn action routine is called "purpose unknown", CheckMorale's and CastMemorizedSpell's comments misstate the code and several meaningful numbers and record offsets are bare; the bytes match and the unit is complete, but a port from the source would be misled.
