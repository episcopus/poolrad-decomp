## Findings

- [ ] should-fix whitepaper 5.14 and the registry notes are stale about the driver: 5.14 says "the five Pascal routines at L2" and that the assembly part "cannot be written in Turbo Pascal without raw bytes and is held (escalated by dec-14, 2026-10-12)", and the `re/symbols.toml` notes of the external entries still say "blocked ... held for the human in escalate-res03-...". The project now keeps such code as the original's bytes and counts the unit complete (`external_from`, ADR for external objects in AGENTS.md); say so in 5.14 ("kept as external object bytes until Phase 5 rebuilds them from an assembly source") and drop the "blocked/held" wording from the notes so a reader does not think work is pending. `work/blockers.md` (line 12) says the same stale thing; that file is the orchestrator's.
- [ ] should-fix the eleven `res03_fn_09E3` .. `res03_fn_1221` declarations (`{@stub} procedure ...; begin end;` in the interface): the registry notes and whitepaper 5.14 say these entries are data inside the driver (tune tables and voice records, "map error (dec-14): not a routine"), yet the source declares them as procedures a caller could invoke. Either remove them from the unit's interface (they have no callers) or comment each one `{ data, not a routine: tune tables and voice records, 08AE:01D7..137C }` so nobody ports a no-op procedure for a table. The names `res03_fn_xxxx` are acceptable for external code the unit does not decompile, but the nine data entries should not carry a routine name at all.
- [ ] should-fix the unit comment says nothing of the time-out the INT 08h handler carries: whitepaper 5.14 [V] says the handler decrements a countdown at `CS:01DB` and, when it runs out, resets the video mode and terminates the program with exit code 255, and calls the voice stepper every tick but chains to the BIOS handler only every 13th (`CS:01D7`). A port that replaces the driver with a platform layer must know about the time-out; put one sentence with the whitepaper reference in the unit comment, and mention that the timer is programmed to 236.7 Hz (divisor 5041, 13 times the BIOS rate, 5.14).
- [ ] should-fix "Tandy SN76489": the unit comment and the SetTandyTune note name the chip. The evidence in our bytes is writes to port `C0h` with the silencing bytes 9Fh, BFh, DFh, FFh (whitepaper 5.14), not the chip type; the part name comes from outside (the Tandy 1000 uses a TI SN76496, which is SN76489 compatible) and should be tagged [H] or reworded "the Tandy 3-voice sound chip on port C0h". The comment also calls 08AE:14EC "the voice stepper for the Tandy" while whitepaper 5.14 only proves the stepper 08AE:1477 (speaker) and the voice records 022Dh/03C7h; the symbols note for SetTandyTune ties 14EC to 03C7h, which is enough for [I], so say [I].
- [ ] should-fix TimeInHundredths QUIRK address: the comment marks `08AE:0033`, which is the `mov ax, 0x1770` that loads the 6000 constant; the 16-bit products are the `mul`s at `08AE:0036` (Minute * 6000) and `08AE:0046` (Second * 100), each followed by `xor dx, dx` that drops the high word (res06's GameClock marks the muls, `0709:0C75` and `0C85`). Use the same addresses. Add the consequence (Minute * 6000 overflows 16 bits from minute 11, so the value falls back by 65536 for each overflowed minute term; Second * 100 cannot overflow) and that this routine is the same code as res06's GameClock (a second copy in this unit), so a port should keep both or document the shared quirk once.
- [ ] should-fix PlaySound: the comment says "any other n starts tune n - 1" but the parameter is `Sound`; fix the stale name. The constants `SoundStop = 0`, `SoundOutputOn = 1`, `SoundQuiet = $FF` are named by effect, good; what the "output flag" is (`CS:020D`, whitepaper 5.14) and that `SetSoundOutput` toggles it for both devices is not said in `SetSoundOutput`'s declaration; add one comment there. `PlaySound(0)` also sets the output off, which makes later `Sound - 1` tunes silent until `PlaySound(1)` (a guess from the names: mark [I]).
- [ ] should-fix SetSoundDriverIdle: `Idle` is stored as a Word but only zero versus nonzero is read in this unit; callers pass 100 (ovl11, StartGame), 0 and `$A` (ovl31 `BeforeRemoval`, `AfterRemoval`; the comment says "10", fine). Say that the value is only tested against 0 here, so "Idle" is a flag whose nonzero values (100, 10) are not used for timing in this unit; if another unit reads `SoundDriverIdle` as a count, add it. Also `ovl11:045D` clears the variable directly (POOLVARS comment), which skips the `StartSoundTimer` that `SetSoundDriverIdle(0)` runs; worth one sentence as a QUIRK in the comment or the whitepaper.
- [ ] note SilenceSound: saves `SoundMode` into `SoundModeBeforePause` before the silent-mode test, so the save also happens when the mode is already 2. This is faithful and matches the bytes (`08AE:017E..01A0` per the note); the whitepaper 5.8 text about Ctrl-S ("reading the pair as a simple on/off switch was too strong") is consistent with it.
- [ ] note WaitHundredths: the comment is correct (the clock falling back by more than Hundredths ends the wait at once, at midnight and at each minutes-term wrap), and it explains why the wait cannot hang. The cases where the clock jumps forward past the target also end it immediately; fine.

What was verified: PlaySound's order against the packet (SoundMode test at `08AE:00DF`, StartSoundTimer when SoundDriverIdle > 0, the three special values 0, 1 and $FF, `Sound - 1` on mode 1 (speaker) and mode 0 (Tandy), the 10-hundredths wait, both tunes cleared, StopSoundTimer); SilenceSound's sequence; SetSoundDriverIdle's branches; TimeInHundredths' multiplications and constants (360000 as `0x57E40` through the LongInt helper, 6000 = `0x1770`, 100); WaitHundredths' loop; the constants' evidence (`SoundMode` values in whitepaper 2.3, `SoundDriverIdle` in `re/dseg.toml`); the unit's directives (`{$A-,F+,S-,R-,G-,I-}` without `O+`, a resident unit); no inline code; the external entries are flagged in the registry and not compared as Pascal.

## Verdict

Passed. No must-fix: the Pascal routines and their comments are true; the findings concern stale held/blocked wording in the whitepaper and the registry, data entries declared as procedures, the missing time-out sentence, an unproven chip name and one QUIRK address.
