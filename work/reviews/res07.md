## Findings

- [ ] must-fix FlushPictureChanges (0464:1B52): the comment says adapter 1 "copies $A000 to $A200 in GC write mode 1". The code, the packet (1D5E `mov ax,$A200` source, 1D73 `mov ax,$A000` destination) and whitepaper 5.23 all say the opposite: the four planes are first written into the off-screen page at $A200 through port 3C5, then `Move(Mem[$A200:..], Mem[$A000:..])` copies that page onto the visible page $A000 (latch copy, GC mode register 5 := 1, restored to 0). A porter who follows the comment copies the wrong way. Fix the comment.
- [ ] must-fix FlushPictureChanges (0464:1B52), and the POOLVARS comments of ds4AD0, ds4C20, ds4D70: the comment calls ds4AD0/ds4C20 "the first and last changed offset of the row" and ds4D70 "the last offset"; POOLVARS says ds4AD0 is the "first changed offset" and ds4C20 the "last changed offset (starts $FFFF)", and the whitepaper 5.23 repeats it. The code (DrawPictureItem 0464:09xx `if ds4C20[R] > DestOfs then ds4AD0[R] := LeftBytes; ds4C20[R] := DestOfs`, the same in 0D71 and 2632, `if DestOfs - 1 > ds4D70[R]`) shows: ds4C20 is the FIRST (lowest) changed byte offset in the staging buffer DrawBuf (a minimum, which is why it starts at $FFFF), ds4D70 the LAST (highest, starts 0), and ds4AD0 is NOT a buffer offset but the screen-side byte column of the first changed byte (LeftBytes: LeftCol * 2 on adapter 0, LeftCol * 1 on adapter 1, LeftCol * 4 on adapter 2). FlushPictureChanges uses exactly that: it moves `DrawBuf^.Data[ds4C20 .. ds4D70]` (length `ds4D70 - ds4C20 + 1`) to `ds4EC0[Row+8]:ds4AD0[Row]+2`. Correct the three POOLVARS comments, the routine comment (and the whitepaper sentence) accordingly.
- [ ] must-fix ShowPicture (0464:1951): "adapter 1 writes one byte per pixel through the four EGA planes" is wrong (also in whitepaper 5.23): each byte holds eight pixels of one plane; the code writes, per row and per cell column, four bytes, one for each plane (map mask EgaPlaneBitMasks[Plane] on port 3C5, `Mem[$A000:ds5050[Row]+Col]`). Also say that the source is the plane-interleaved layout of adapter 1 (4 bytes per cell). The comment also speaks of "(X, Y)" and "column X*2" where the parameters are PicCol and PicRow (PicRow * 8 is the first pixel row).
- [ ] must-fix RemapPictureColours (0464:1E5C): the header says the changes go to a scratch copy "that is copied back over the items from FirstItem on at the end", and the local `Items` is described as "ItemCount for a negative FirstItem ..., then 1". Because of the QUIRK at 1F51 (which the comment documents correctly) `Items` is 1 in the colour loop on every path, and the copy back is `Items * ByteSize` after the loop, so the routine ALWAYS recolours and copies back exactly ONE item: item FirstItem (item 0 for a negative FirstItem). It is never "the items from FirstItem on". All 13 callers pass FirstItem >= 0 (ovl18 AnimateAreaDoors passes the door frame index, the others 0). Say "recolours item FirstItem only", and that the scratch copy of a negative FirstItem holds ItemCount items but only item 0 is used. As written a porter would recolour a range.
- [ ] must-fix FillPictureRect (0464:2632): the comment says it "fills the Width x Height cells of picture Target whose top-left cell is (FirstCol, FirstRow)". Only the column unit is cells: Width and FirstCol are cells (8 pixels; 2, 4 or 1x4 bytes per cell), but FirstRow and Height are PIXEL rows: `TrackRow := FirstRow; DestOfs := TrackRow * WidthCols`, `LastRow := Height - 1`, one loop pass per pixel row, no `* 8` anywhere; ovl29 DrawWallDescriptors calls it with `$10, $B` / `$3B, 1` / ... i.e. a pixel row start and a height of $2B pixel rows. A porter who reads "cells" fills eight times too many rows. State the units (the whitepaper 5.23 Fill paragraph says "Width x Height cells" and "X = 2, the wall descriptor rows" too). The caller list is also incomplete: the packet shows `ovl16:34DF ovl16_fn_34DF` besides DrawWallDescriptors, and whitepaper says "called four times".
- [ ] should-fix stale parameter names in comments: LoadPicture ("block A", "B = the pixel-buffer flag", "C = the colour key"; the parameters are BlockId, AllocFlags, Color), SetVideoMode ("video mode A"), MirrorByte, MirrorWord and SwapNibbles ("of X"; the parameter is Value), ShowPicture ("(X, Y)", "X*2"), FillPictureRect ("X"). Use the real names.
- [ ] should-fix the `retf n: ...; n bytes of locals` prefixes of ColorMatchMask, PaletteColor and the stray first comment line above DrawPictureItemClipped ("0464:0D71: retf 16: same frame as DrawPictureItem. Bit 0 of Flags is tested.", followed by a second comment with the same address) duplicate the address and add nothing; keep one comment per routine (res06 review did the same).
- [ ] should-fix RestoreVideoMode (0464:00FF) and SetVideoMode (0464:00CF): `SetVideoMode` copies the current mode ds4A1D to SavedVideoMode before setting the new one, so `RestoreVideoMode` (= `SetVideoMode(SavedVideoMode)`) also overwrites SavedVideoMode with the mode it just left: two Restore calls in a row toggle between the two modes, and after one Restore SavedVideoMode holds the game's graphics mode, not the original one. That side effect (and who reads SavedVideoMode afterwards, QuitGame) belongs in the comment, ideally as a `QUIRK 0464:00FF`. The SetVideoMode comment says it is called "by res08_init with $0D"; RES08 also calls it with 9 (line 59) and 4 (line 64) for the other adapters, and ds4A1D / SavedVideoMode are described in POOLVARS as "reader unknown" and "no writer is in the decompiled units", which this unit contradicts (it reads and writes both). Update those two POOLVARS comments; ds4A1D is the current video mode (it is set to Mode at the end of SetVideoMode) and could be renamed (`CurrentVideoMode`) with `make rename`.
- [ ] should-fix the shared global loop counter ds70C7: five routines (DrawPictureItem, DrawPictureItemClipped, RemapPictureColours, UnpackPicturePixels's callers' sibling FillPictureRect) use the global `ds70C7: ShortInt` as the control variable of `for` loops, and POOLVARS still describes it only as "loop counter of FreeSpriteList". None of the routines says why a global is used (the original did: the lesson `res07-global-loop-counter`). Worse, the packet shows the limit is a hidden BYTE temporary compared signed (0A3D `cmp al,[bp-19]; jg`), so a limit of 128 or more (SrcRowBytes, VisibleBytes, Count) is truncated and would skip or misrun the loop. Real calls stay below that (the pictures are narrow), but this is exactly what a port must know: add a `QUIRK` (with the address of the `jg`) in DrawPictureItem and DrawPictureItemClipped, and widen the POOLVARS comment.
- [ ] should-fix globals that are still `dsXXXX` although this unit shows what they are: ds4A28 (per pixel row "changed" flag of the staging buffer), ds4C20/ds4D70/ds4AD0 (first buffer offset, last buffer offset, screen column; see above), ds4A24 (the save-under buffer of DrawPictureItemClipped bit 2), ds5370 (clipping on), ds4EC0/ds51E0 (the segment of each pixel row for adapters 0 and 2, used by ShowPicture and FlushPictureChanges), ds5050 (the EGA row offset of each pixel row, `Row * 40`), ds25FA, ds0D02, ds0D06 (the pixel pattern tables, already well commented). The names are the main readability gap of the unit: every blitter reads like `ds4C20[FirstRow] > DestOfs`. Rename those with evidence by `make rename` (the decompiler's lane; ds4A28 and ds4C20.. also need the corrected comments above).
- [ ] should-fix meaningful numbers left bare: the VGA/EGA port numbers and values in ShowPicture and FlushPictureChanges (`$3C4/$3C5` sequencer index/data with register 2 = map mask, `$3CE/$3CF` graphics controller, register 5 = mode, 1 = write mode 1, `$0F` all planes), the segments `$A000`/`$A200` (visible page, second page: $A000 + page * $200, as RES06 names with SetPageSegment), the viewport geometry `$A7`/`$A8` (168 pixel rows), `$28` (40 bytes per row), `$150`/`$A8` (168 words, 168 bytes) and the `Row + 8`, `+ 2`, `+ 1`, `+ 4` offsets in FlushPictureChanges (the staging buffer is the 21x21 cell window that sits at cell (1,1) of the screen: 8 pixel rows, one cell, i.e. 2 bytes on adapter 0, 1 on adapter 1, 4 on adapter 2; the comment never says so, and a porter cannot guess it), the header size `$17` and the pixel data offset `$11` (AllocatePicture, ReleasePicture, LoadPicture), and the flag bits `Flags and 1` (masked) / `Flags and 4` (save background) / `AllocFlags and 1` (pixel buffer), which only the locals HasMask and SaveBackground of DrawPictureItemClipped name. RES06's review asked for named ports and registers; use the same style (`SeqIndex`, `GcMode`, `PictureHeaderSize`, `BlitMasked` ...).
- [ ] should-fix LoadPicture (0464:0111): the parameter `Text` says nothing (it is the DAX file name without '.dax': `DaxName`/`SetName`); the comment does not say what happens when `LoadDaxBlock` returns `Size = 0` (nothing is loaded, Target stays nil, no message, FlushKeyboard is skipped), and does not say that Color is the transparent colour (the pixels equal to it get a 1 bit in the Pixels buffer and a 0 bit in the data, which DrawPictureItem then keeps from the destination) nor that AllocFlags bit 0 requests that buffer. That mask convention (1 = keep the destination) is only implied by DrawPictureItem's comment; state it once in UnpackPicturePixels or the unit comment.
- [ ] should-fix UnpackPicturePixels (0464:02A5): the parameter `Data` (the picture being filled) has the same name as the record field `Data` that `with PPicture(Data)^ do` makes visible, so `Data = nil` and `Data[OutOfs]` mean two different things; rename the parameter (`Picture`, `Dest`). `Source`/`Offset` are the DAX block and the byte offset of its pixel data ($11 from LoadPicture); the comment says so.
- [ ] should-fix AllocatePicture (0464:248E) and whitepaper 5.23: the comment says "times 2 again when the video adapter is not 0, the EGA planar case". The doubling applies to adapter 2 (4 bytes per 8 pixels, the chunky 4-bit layout) as well as to adapter 1 (the EGA planar case), so "the EGA planar case" is only half true. Also say that Height is in pixel rows and WidthCols in cells of 8 pixels (the TPicture field comments only give the offsets; the units are visible in DrawPictureItem `SrcLastRow := Height - 1`, `WidthCols * 2/4`) and that ItemBytes/ByteSize is bytes per item.
- [ ] should-fix whitepaper 5.23 (checklist 10): besides the wrong sentences listed above (ShowPicture one byte per pixel, "first and last changed offset" of the three tracker arrays, FillPictureRect "cells" and "called four times"), the "Map corrections" and "compiled with O+" bullets still say "all 14 matched routines" and "res07 has 19 routines plus the empty initialisation part" (the unit now has 19 routines and the init, all matched: 20). The learnings `picture-record-fields` and `colour-remap-structure` in `re/learnings/res07.toml` are retrieved into every packet as [V] and contradict the source (they call +0 "a word (the row/item count)", +8 "the height in rows", +$11 "the bytes per row", the routine `res07_fn_1E5C` with a `FirstRow` parameter): the source and `TPicture` are right (+0 Height in pixel rows, +8 ItemCount, +$11 ByteSize bytes per item); correct or retire those two lessons.
- [ ] should-fix DrawPictureItemClipped (0464:0D71): the comment has no list of callers (ovl18 AnimateFinalPicture and ShowEndingNarrative, ovl28 DrawSprite and Show3DSprite, ovl31 RemoveCombatant, ovl32 DrawIcon, res12 1CBA/1CE0/1FEB) while its siblings do. The QUIRK sentence "the adapter 1 mask phase is set once per call, so it carries from row to row" is true but harmless (VisibleBytes is a multiple of 4, so the phase is back at 4 after every row); say so or the quirk looks like a bug a porter must reproduce. Same for DrawPictureItem adapter 1: `LeftBytes := LeftCol` (one byte per cell) where adapters 0 and 2 use `* 2` and `* 4`: the screen-side column unit, see the ds4AD0 finding.
- [ ] note names: `Colour` (FillPictureRect, RemapPictureColours) and `Color` (ColorMatchMask, PaletteColor, SetPaletteRegister, LoadPicture, TPicture comments) are both used in one unit; whitepaper and the other units use `Color`. Harmonise in Phase 6, not a blocker.
- [ ] note SetPaletteRegister (0464:2A0D): comment, mapping (0..7 as is, 8..15 as +8 = 16..23) and the callers (ovl01 ShowTitleScreen, ovl31_e2/e3) match the code and the packet; `Register` could say "EGA palette register 0..15". It never tests VideoAdapter; the callers do.
- [ ] note ColorMatchMask, PaletteColor, MirrorByte, MirrorWord (GlyphPixelMasks words $C000..$0003 in the opposite order, as the comment says), SwapNibbles, AllocatePicture, ReleasePicture, UnpackPicturePixels adapters 0 to 2 and DrawPictureItem were read against the packet and are accurate apart from the findings above. `MirrorPicture` mode 2 "in place" for the pixel buffer is loose (the buffer is mirrored into the same reversed position as the data, `Dest^.Pixels[DestOfs]`, not literally in place); the res12 callers are confirmed by the packet (res12_fn_18CF).

## Verdict

Not passed: five must-fix findings (FlushPictureChanges copy direction, the tracker array semantics, ShowPicture's "one byte per pixel", RemapPictureColours' "items from FirstItem on", FillPictureRect's cell units); all five are comment corrections, no byte changes.
