## Findings

- [x] must-fix BlockTerrainFlags (ovl10:08A4): the QUIRK says "codes 3 and 4 are listed twice; the first entry (3) wins" and whitepaper 5.5.2 repeats it, but the table has eight overlapping codes, not two. Recomputed from the source (and the packet's compare chain 08AD..0A.., which tests the arms in source order, so the first listed arm wins): `3`, `4` (Flags 3 beats 2), `7` (3 beats 2: `6..7` against `7`), `$28`, `$29`, `$2B` (1 beats 5: the first line `$28..$29, $2B` against `$27..$2C`), `$7C` (8 beats 9: `$79..$7C` against `$7D, $7C`) and `$F5` ($20 beats $80: `$4E, $F5, $E8..$E9` against `$6D, $F4..$F6`). A port that rebuilds the table as a lookup, as one would, must keep the first value. List all eight codes with the winning value in the QUIRK (the duplicates are what the decompiler had to keep to match), and fix whitepaper 5.5.2's QUIRK line the same way. The comment "A code no range lists leaves the result unset" is true (an uninitialised `Flags`); mark that as its own QUIRK with the address of the missing default, since a port must define it. (fixed in 975fe2b)
- [x] should-fix PrepareCombatants and the constants `KindMask`/`ComputerRun`: the unit calls the low seven bits of `B84` its "kind" (`KindMask = $7F`, "B84 kind is 0 or above $66") but names word 710 `Var2Morale` and writes `B84 := Morale + $80`, and ovl09's CheckMorale (whitepaper 5.5.3) reads `(B84 and $7F) * 2` as a morale threshold and ignores values above $66. Within the unit the two names for one value disagree. Use one (the morale reading is better supported: ds6825 "AI morale scratch", whitepaper 5.5.3), name `$66` (a bare constant in `PrepareCombatants`: the largest valid morale value), and keep [I] on it as `Var2Morale` already does. (fixed in 975fe2b)
- [x] should-fix globals still named `dsXXXX` whose comments already say what they are: `ds6AAD`/`ds6AAE` (the party's column and row in the 16x16 area map, POOLVARS), `ds6AAF` (the party's facing: this unit uses it as the direction 0..7 into `ds2736`/`ds273F` and `shr 1` as the facing 0..3, while POOLVARS says "the marker's icon set"; either the POOLVARS comment is incomplete or the name is two things: say which), `ds2736`/`ds273F` (the x and y steps per direction, nine entries each; ovl31 and ovl14 use them too), `ds84DC` (an outdoor/wall-view mode, 0 and $A skip), `ds6B00`/`ds6B05` (HEAD and BODY bank indexes, $FF when none). Rename them with `make rename` (`PartyCol`, `PartyRow`, `PartyFacing`, `StepX`/`StepY` or `DirDX`/`DirDY`), at least the ones this unit uses ten times. `ds6E30` and `ds6DE3` are named by ovl08's review (Magic toggle, round counter). (fixed in 975fe2b)
- [x] should-fix StartBattle comment: it lists what is reset but leaves out `ds6B00 := $FF` and `ds6B05 := $FF` (the HEAD and BODY bank indexes, "no sprite loaded"), `res12_fn_2B88` after the view origin is set, and `DiscardWaitingKey` between the builders (key presses typed during the setup are dropped). Name them; whitepaper 5.5.2 says "frees ... the HEAD/BODY sprites", which needs the index reset to be complete. (fixed in 975fe2b)
- [x] should-fix magic numbers: `$FF` (the loop that clears `CombatantTable`, with the real bound the 72 combatants of whitepaper 5.5.1), `RingCells > 11` in FindStartCell (the ring length: 12 cells, no relation to the `GridLastCol` it appears beside), `PassageKind(...) <> 1` (twice; `SideWall`), `DirNone` is named but `FacingCombatDir[(Facing + n) mod 4]` uses bare 1, 2 and 3 (the three other sides of the facing; name them as offsets). The dungeon pictures of DrawNorthWestCorner and DrawNorthEastCorner ($F, $12, $10, $14, $18, $B, $13, $E, ...) are bare picture ids in nested decision tables, which the whitepaper calls "the compiler proof of every picture table"; the pictures' meaning (wall diagonal, door, corner) is not named anywhere. - [x] should-fix FindStartCell: the comment describes the walk correctly but in one paragraph; the three phases (`Phase` 1 starts a ring, 2 and 3 step to either side), `OutOfGrid` and the group fallback are not marked inline. Add comments at the three `case Phase` arms and the group loop (`while (Group < 3) and (Phase <> 1)`). `TryPlaceAt` writes `CombatantTable[Index].X/Y` before it probes, so a failed try leaves the cell it probed in the table (a side effect FindStartCell relies on when it returns False for a NoBody combatant that is cut out): mark `QUIRK ovl10:1434` or say why it is harmless. - [ ] note PlaceAllCombatants: `Flag10D = 0` characters are placed and then taken off again, leaving a body unless NoBody or a duel: this agrees with ovl08, where `Flag10D = 0` ends a character's turn (the character is out of the fight). The routine calls `BlockTerrainFlags` five times in a row (the table is searched each time), which is faithful.
