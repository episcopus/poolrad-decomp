## 0. Result

* **Ideas 1, 2, 4, 5, 6 and 7 are built and measured (section 4b)**, 16 of 16 sessions passing after each: banks -5.9 %, image -19.7 %, storage requests -30 %, game CPU -0.8 %. The estimates of section 4 for 4, 5, 6 and 7 were 3 to 6 times too high; 2 was better than estimated.

* **The seventh bank slot is built [V]** (blocks `$3C`, `$3D`, which `DSKCON` leaves alone: `src/engtest/t_hide.c`). With the groups chosen again for seven slots (`data/bank_groups.json`: 37 banks) the bank loads of the
  15 sessions are **2,760** (6,972 before this step, 20,123 at the start of 8.9a): **-60 % and -86 %**. `parley-combat` 311 loads (2,335 at the start). 16 of 16 sessions match, the 63 member stress build passes.
  One honest change in the checker: the camp's fire flickers by the game's random numbers and how many frames were drawn depends on the machine's speed, so after the speed-up the final screen of `camp-save`
  differs from the original's in the dither of the animated picture (676 pixels, all inside the picture window; the files and DGROUP are equal). `tools/gamecheck.py` now accepts a labelled screen of such a session when it equals the golden
  picture everywhere outside that window, and **says so** (`equal outside the animated picture window (N pixels differ inside it)`).
* **Research, with numbers** (sections 2 and 3): the code is 95 % instruction code and its bulk is the calling convention and the far pointers' accessors, not strings or duplicates; the data has **330 KB of exact duplicates (26 %)**
  that the image stores twice; ZX0 would take the image from 10.7 floppies to about 4.4, but its decoder (measured on the emulated 6809: 68 cycles an output byte; LZ4 31.6) makes it a capacity measure, not a speed measure. Section 4 ranks the ideas.

## 2. Code size: what the 318 KB are made of [V]

`tools/codestats.py` sweeps the code of every bank with the disassembler (code 318,229 bytes, rodata 16,013, the entry tables 1,530; nothing else is in a bank). Frequent instructions by the bytes they occupy:

| Instruction | % of code | | Calls (JSR, LBSR) by target | bytes | calls |
|---|---:|---|---|---:|---:|
| `PSHS` | 11.2 | | `push4ByteStruct` (a 32 bit value by value) | 14,145 | 4,715 |
| `LDB` | 10.6 | | `vm_bp` (a record of the banked heap) | 8,802 | 2,934 |
| `LEAS` (frames and cleanup after calls) | 10.4 | | far stubs (a routine of another bank) | 7,215 | 2,405 |
| `LEAX` | 10.0 | | `vm_ptr` (a paged global) | 3,981 | 1,327 |
| `JSR` | 9.4 | | inside the bank | 3,482 | 1,164 |
| `LBSR` | 7.7 | | `copyDWord`, `initDWordFrom*`, `isDWordZero`, `cmpDWord*` | about 9,000 | 2,700 |
| `TFR` | 7.1 | | all calls | 54,476 (17 %) | |

The listing of one small routine (`ComputeSavingThrows`, generated by `cmoc -S`; `build/run/asm/mk.sh UNIT`) shows why: one expression `Character->SavingThrows[i]` on a record of the banked heap is **about 35 bytes**:
`LEAX param; LEAS -4,S; LBSR push4ByteStruct; JSR vm_bp; LEAS 4,S; TFR D,X; LEAX 109,X; TFR X,D; ADDD ,S++; TFR D,X; LDB ,X`. The 32 bit far pointer is copied onto the stack by a library routine, the accessor is called, and the index
arithmetic goes through `TFR` three times. Other findings [V]:

* **No fat in the data around the code**: strings and tables are 16 KB in all; **duplicated code is 1.2 KB** (identical function bodies, 8 groups); the 16 functions over 2,000 bytes are 54 KB (17 %), 860 functions average 370 bytes.
* **25 % of the code (80 KB, 282 routines) is never run by the 17 sessions** (`tests/sessions/coverage.json`): character training, treasure building, the ending, most spells. It cannot be dropped, but it is what the banks load least.
* **16 bit far pointers would save 3.8 %** (`farptr` as `u16` in a scratch include directory, every unit recompiled and measured: 472,920 to 455,000 bytes over the units and their split parts; it does not link, it only measures).
  Less than the 4,715 `push4ByteStruct` calls suggest, because the pointer still has to be pushed.
* **CMOC has no size switch beyond `-O2`** (`cmoc --help`: `-O0/-O1/-O2`, `-fomit-frame-pointer`, which is on).
* The sources of the biggest repeated cost: `FPB` (banked records) occurs **2,696 times** in the translated game and **2,098 of them name a pointer the same function used before** (`CreateCharacter` alone: 140 uses of one pointer).

## 3. Assets [V unless tagged]

### 3.1 Exact duplicates: 330 KB, free

`tools/assetstats.py` and a hash of every unpacked block: the eight tileset files of each family (`PIC1..8`, `8X8D1..8`, `BODY1..8`, `HEAD1..8`, `SPRIT1..8`, `CPIC1..8`, `WALLDEF1..8`) hold blocks that are **identical across tilesets**; the PC shipped them
once per tileset disk. 229 groups, **329,691 bytes of the shipped 1,273,124 (26 %)**: `PIC` 152 KB, `8X8D` 42 KB, `BODY` 35 KB, `SPRIT` 34 KB, `CPIC` 27 KB, `WALLDEF` 14 KB, `HEAD` 14 KB. `mkimage.py` stores every entry's block separately (1,287 entries, 1,287 distinct offsets).
Letting identical blocks share one copy changes no runtime code (an entry is an offset and two sizes). Near-duplicates add nothing: the unique versions compress as well alone as together (lzma over all versions of a block id: 0 % better).
The floppy volumes of 8.4 are per file, so a shared block needs a common volume or one copy per volume that holds a user; that is a layout question for the distribution.

### 3.2 Compression: what it buys and what it costs

Sizes (the real `zx0` and `lz4 -9` of the toolchain image and the host; ZX0 is 45 to 55 % of RLE on the data):

| | as shipped / in the image | ZX0 | LZ4 -9 |
|---|---:|---:|---:|
| the 37 code banks | 335,772 | **138,041 (41 %)** | 181,472 (54 %) |
| all DAX blocks (RLE of the original) | 1,273,124 | 695,905 (55 %) | |
| the 845 unique DAX blocks | 943,433 | **515,188 (55 %)** | |
| picture families (PIC) | 462,832 | 247,184 | |
| image today: blocks | 1,633,630 | | |
| image with dedupe | 1,303,939 | | |
| image with dedupe and ZX0 (banks, data, core 22 KB) | | **about 675,000** | |

So the image goes from **10.7 floppies of 153 KB to 8.5 with dedupe and about 4.4 with dedupe and ZX0**.

Speed, measured on the emulated 6809 (`probes/zxbench.c`, `probes/lz4bench.c`; the decoders are written for it: `tools/zxbench/`; the ZX0 one is checked against the real `dzx0` on two samples, `tools/zxbench/dzx0.py`, and by the sum of the output on the
CoCo; both decode a 6,184 byte code bank into two MMU blocks, the sample `ovl25`):

| Decoder | cycles an output byte | output KB/s | compressed size of the sample |
|---|---:|---:|---:|
| ZX0 (a plain decoder: bit queue in A, lengths in memory) | **68.3** | 25.6 | 2,858 (46 %) |
| LZ4 block | **31.6** | 55.3 | 3,769 (61 %) |
| the original RLE (`k_rle`) | about 20 to 25 [E, research 03] | | |

Time to bring this 6,184 byte bank in, reading plus decoding [E, from the measured decode times and the research notes' media speeds]:

| Medium | uncompressed | LZ4 | ZX0 |
|---|---:|---:|---:|
| floppy through DSKCON, 12.6 KB/s | 0.49 s | 0.41 s (-16 %) | 0.46 s (-6 %) |
| DriveWire 115,200 bps, about 11 KB/s | 0.56 s | 0.45 s (-20 %) | 0.50 s (-10 %) |
| SDC command mode, about 100 KB/s [?] | 0.06 s | 0.15 s (+150 %) | 0.27 s (+350 %) |

**Compression is a capacity measure, not a speed measure**: on the floppy and on DriveWire it saves about as much read time as the decoder costs; on an SDC it loses. A decoder twice as fast (unrolled, tuned) would make ZX0 a win on the slow media, not on the SDC.
This points to a build option per medium (compressed for floppy sets, plain for SDC) rather than one packing. The engine has 650 bytes free; a ZX0 decoder is about 200.

### 3.3 The image's index in RAM

`img_find` reads the entries of a file from the image a chunk at a time: in `parley-combat` 2,172 index requests next to 1,287 bank reads, 8 % of all requests (`tools/seclog.py`). The 1,246 entries are 12 KB, which fits the free part of the two index blocks (`$06`, `$07`).
Reading them once at mount removes those requests (each is a seek and a sector on a floppy).

### 3.4 What a session touches

The 17 sessions read **18 % of the data bytes** (225,765 of 1,275,191) but 96 % of the code banks and all of the core. Data is read lazily, so the order of files on the disks matters more than their total size:
the town, the tilesets of the first areas and the combat set first, the ending and the late tilesets on the last disks.

### 3.5 The picture store

At the end of a fight or a walk the store holds about 115 KB in 47 to 57 pictures; **two 128 tile banks of 24x24 pixels are 73.7 KB of it (63 %)**; the masks (4 bits a pixel, one colour key bit of information) are 17 to 20 % (about 21 KB). Peak 9,168 of 9,728 units in every session.
Ideas: load only the tiles of the current map, or keep masks at one bit a pixel (about 15 KB). Either would free blocks for bank slots [E, not measured: how many distinct tiles a map uses is not known yet [?]].

**Idea 6, what was built.** The record layout and the files keep four bytes per pointer, so the 16 bits cannot be the type of a field. A banked pointer became a handle: the high word of the `farptr` is 0, the low word is `page << 13 | offset`
(page 0 starts at offset 8 so that 0 stays nil). C's own conversions between `u16` and `u32` then keep the high word 0 and no expression of the generated code changes. `vm_bp`, `vm_pkp` and `vm_far` take the handle; `rtl_getmem`,
`rtl_far` and `statecheck.py` produce and read it. Step 6a (only the accessors) was **bigger** by 3,790 bytes: CMOC converts a `u32` to a `u16` with a library call (`initWordFromDWord`), which costs more than the 4 byte push it replaced.
Two things fixed that: `tools/narrow.py` types the locals, by-value parameters and results of the banked pointer types as `hptr` (178 parameters, 223 locals, 5 results; not the routines reached through a procedure variable or defined outside the generated
units; not a variable whose address is taken), and the 557 uses that remain on 32 bit variables read the low word where it is (`FPBL`). CMOC 0.1.100 -O2 crashes (segmentation fault) on one statement of `ResolveCombatantAttacks` once its
parameter is a `u16`; a patch in `mkgame.py` goes through a local pointer. **Why it buys so little [V]**: most uses of banked pointers were already by-reference (idea 5) or hoisted (idea 4), and the fields, which are still four bytes, are where most reads start. The bound of
-5.8 % assumed every `farptr` narrow, fields and globals too. Going further means changing record layouts, the D7 decision on the save format.

What the six ideas did not buy: bank loads (they rose from 2,760 to 3,652 because the units now split differently; a finer split of `ovl16` is the way back) and speed (game CPU -0.8 %). The code is 6 % smaller and the image 20 %; the game is not faster, because the cost is in the
far calls, the data windows and the drawing, not in the instructions the ideas removed.
